# 스토리 프롬프트 출력 검토

검토 주체는 구현 에이전트다. 실제 사용자의 재미 확인이나 사람의 출력 검토를 대신하지 않는다.

## 인터뷰

- `story-creation-baseline-1789228953946.md`: 수정 전 `98e248d` 프롬프트, 15개 응답 중 12개가 기계 검사에서 실패했다. 도구 스키마는 수정본과 같다.
- `story-creation-candidate-1789228916371.md`: 수정본, 3회 45개 응답이 기계 검사를 통과했다. 상한에서는 더 넣을 수 없다고 알리고 기존 화를 보존했다. 추가 제안은 앞 화가 성공했다고 가정하지 않았다.
- 앞선 `story-creation-candidate-1789227837516.md`는 당시 기계 검사를 통과했지만, 전문 검토에서 상한 안내 누락과 “문제를 해결한 뒤”라는 결말 가정을 발견했다. 그 결과를 최종 통과 근거로 쓰지 않는다. 검사와 프롬프트를 보강하고 위 묶음으로 다시 실행했다.
- iOS에서 짧게 끊긴 입력 `비` 뒤에 질문을 두 번 하는 답을 확인했다. 이 입력과 구체적인 상황, 추가 의사까지 이어지는 대화를 아홉 번째 회귀 사례로 넣었다.
- `story-creation-candidate-1789229655647.md`는 보강 도중 54개 응답 중 1개가 실패한 기록이다. 질문 하나만 쓰는 예시를 추가한 뒤 다시 평가했다.
- 최종 `story-creation-baseline-1789229836524.md`: 같은 아홉 대화에서 수정 전 프롬프트의 18개 응답 중 11개가 실패했다.
- 최종 `story-creation-candidate-1789229732993.md`: 새 프롬프트로 3회 실행한 54개 응답이 기계 검사를 통과했다. 짧은 입력과 추가 의사에 대한 답도 세 번 모두 질문 하나만 썼다. 호출 실패는 없다.

## 방향 중심 지침 적용 뒤

- 문장·문단·물음표 수와 서식 유무를 기계 합격 기준에서 뺐다. 이전 54개 통과는 이전 기준의 기록이다.
- `story-creation-baseline-1789231085512.md`: 최초 구현 전 `98e248d`는 새 기준으로 19개 중 7개가 실패했다. 카드 계약의 판별력을 확인하는 비교다.
- `story-creation-baseline-1789231152737.md`: 직전 `1718301`은 카드 검사 19개를 통과했다. 같은 육아 갈등 입력에 두 문장 한 문단으로 답했다. 이 기록은 글의 모양을 비교하는 기준이며 기계 검사가 가독성까지 판정한다는 뜻이 아니다.
- `story-creation-candidate-1789231093834.md`: 방향 중심 첫 적용은 상한 안내 2건이 실패했다.
- `story-creation-candidate-1789231163873.md`: 상한 보강 뒤 기계 검사는 통과했지만, 전문에서 교환 성공과 아기가 잠든 결과를 전제한 추가 제안을 발견했다. 제품 규칙과 회귀 검사를 보강했다.
- 현재 `story-creation-candidate-1789231246240.md`: 3회 57개 응답이 기계 검사를 통과했고 호출 실패는 없다. 육아 갈등 답 세 개는 모두 문단과 목록으로 장면과 답할 내용을 나눴다. 직전 프롬프트와 같은 입력의 출력으로 비교했다. 앱에서의 가독성은 사용자의 리뷰를 기다린다.
- **현재 전문 검토는 미통과다.** 2번째와 3번째 `추가 의사 뒤 합의`는 각각 새 제품 설치, 교환 절차 완료를 전제로 제안했다. 1번째와 2번째 `서로 다른 두 상황`에서는 두 화의 빈 부분을 함께 물었다. 일부 답에는 `사용자` 호칭과 합니다체도 남는다. 기계 검사의 통과를 전체 대화 품질 통과로 보고하지 않는다. 이후 구현에서는 이 사례의 출력과 카드 조건을 함께 재검토한다.

## 사용자 역할을 인물로 만들지 않기

- `story-creation-candidate-1789231709183.md`: 사고 정보 교환 사례를 추가해 전체 3회 60개 응답을 평가했다. 59개가 기계 검사를 통과했고 1개가 실패했다.
- 사고 사례의 첫 두 카드는 characters와 cast에 상대 운전자 Daniel 한 명만 넣었다. 사용자의 목표는 details에 남아 별도 인물로 복제되지 않았다.
- 세 번째 사고 사례는 상대의 성격을 다시 묻고 카드를 내지 않아 실패했다. 입력에는 장소, 상대, 사건과 목표가 있으므로 바로 카드가 나와야 한다. 이 반복 검증은 전체 통과가 아니다.
- 사용자 역할을 추가한 잘못된 카드를 상대 인원 검사에서 떨어뜨리는 단위 테스트를 추가했다. 인원 검사만으로 인물 역할의 의미까지 판정하지는 않는다.

## 각본과 다음 화의 기존 평가

- `story-play-baseline-1789229190787.md`: 이전 각본 프롬프트는 첫 화에서 누수 영상을 빠뜨려 실패했다. 같은 두 화 카드에서 이전 요청과 같이 상세 상황을 보내지 않았다.
- `story-play-candidate-1789229092146.md`: 각본 3회 모두 영수증과 영상을 유지했고 두 화를 생성했다. 두 번째 화의 도입은 교환 성공을 가정하지 않았다.
- 비교용 기억은 고정 입력이며 실제 사용자의 플레이 기록이 아니다. 같은 다음 화에서 첫 응답과 후속 응답을 각각 비교했다. 첫 응답만으로 차이가 충분하다고 판정하지 않았다.
- 후속 질문은 지난번 가져온 기계에 맞춰 설명해 줄 수 있는지 묻는다. 모델을 확인한 기억에서는 다시 설명할 필요가 없다고 답했고, 확인하지 못한 기억에서는 모델이나 사진을 요청했다. 3회 모두 필요한 설명이 달라졌다.
- 이전 시도에서는 매장 체험 기계를 쓰는 데 집의 기종부터 요구하는 답을 발견했다. 지금 상황에 필요하지 않은 정보를 장애물로 만들지 않도록 규칙을 보강했다.

## 남은 확인

앱에서 두 화를 플레이한 뒤 사용자가 원하는 상황, 전개에 대한 궁금함, 앞 화의 영향에 관해 직접 답해야 한다. 위 평가만으로 재미를 확인했다고 보지 않는다.

## 2026-09-13 재검증 (`1012eb2`)

제품 코드는 바꾸지 않고 검증했다. 실제 모델은 기존 API와 같은 `openai/gpt-5.6-luna`다.

### 인터뷰와 대본

- `story-creation-candidate-1789232195624.md`: 3회 60개 응답 중 기계 검사 58개 통과, 2개 실패, 호출 실패 0개다. 1회 추가 제안은 `커피 머신을 교환한 뒤`를 전제로 했다. 2회 사고 입력은 장소·상대·사건·목표가 있는데도 상대 성격과 경찰 호출 의사를 되물으며 카드를 내지 않았다.
- 의미 검토에서도 미통과다. 1회 `서로 다른 두 상황`은 두 화의 빈 부분을 한꺼번에 물었다. 2회 비행기 제안의 `사용자는`, 2회 두 상황 확인의 `정하지 않겠습니다`처럼 호칭과 말투 문제도 남는다. 사고 카드가 나온 두 회는 상대 운전자 한 명만 넣고 플레이어를 복제하지 않았다.
- `story-play-candidate-1789232195008.md`: 대본 3회 모두 기계 검사를 통과하고 영수증·누수 영상과 두 화를 보존했다. 고정 기억 비교에서 기종을 확인한 경우에는 다시 설명할 필요가 없다고 하고, 확인하지 못한 경우에는 기종이나 사진을 요청했다. 이는 실제 플레이가 아닌 비교 입력의 결과다.
- 대본 의미 검토는 전부 통과라고 판정하지 않는다. 3회 2화 stage에 `이전 교환의 성공이나 실패는 이 상황에 영향을 주지 않는다`가 있어, 사건 유지와 실제 결과의 반영을 혼동할 여지가 있다. 1회 성공 기억의 첫 답도 교환을 `fixed the leaking machine`으로 표현해 사실 보존을 더 확인해야 한다.

### 실제 앱

- 대상은 현재 worktree의 API 3951, Metro 8132, iOS `flyn-slot-5`와 Android `flyn_dev_2`(`emulator-5564`)다. 설치된 Development Build를 재사용했다. 기기 초기화나 DB 변경은 하지 않았다.
- iOS에서 `커피 머신 매장` 두 화를 새로 만들고 완주했다. 1화는 교환 없이 누수 원인과 점검 방법을 묻고, 2화는 다른 날 같은 직원에게 자신의 머신 세척 방법을 배우는 상황이다. 영수증·영상은 1화 도입에 남았고 상대는 Daniel 한 명이었다.
- 1화에서 느슨한 실링과 먼지를 확인하고 점검을 마쳤다. 표현 돌아보기의 `2화 시작하기`로 제작 인터뷰 없이 2화에 들어갔다. `Can you adapt the cleaning instructions to the machine I brought last time, or do you need me to explain it again?`에 Daniel은 `I remember the machine and the loose tank seal we checked last time. You do not need to explain it again. We can use its own cleaning steps, starting with the water tank.`라고 답했다. 실제 기록이 설명의 시작점에 반영됐다. 2화 종료 뒤 `마지막 이야기까지 함께했어요`를 확인했다.
- 이 실제 플레이는 성공 결과 한 경로다. 서로 다른 실제 결말의 비교와 중간 재진입은 이번 실행에서 확인하지 않았다. 에이전트 플레이이므로 사용자 재미 확인을 대신하지 않는다.
- iOS 기본 크기에서 버튼 안의 `대본을 쓰고 있어요`, 진행 표시, 비활성화와 카드 뒤 안내 숨김을 확인했다. 생성 뒤 표지가 있는 상세가 열렸다. 표지·저장 단계는 이번 화면 캡처에서 따로 확보하지 못했다. 세 단계의 버튼 문구와 실패 복원은 화면 단위 테스트 11개로 확인했다. 전체 타입 검사도 통과했다.
- iOS 다크 모드와 Android 다크 모드에서 카드를 읽을 수 있었다. Android 5화 카드의 추가 버튼 비활성화와 상한 안내를 확인했다. Android 기본 크기에서 다크 모드로 전환한 직후 입력 안내가 검정으로 남는 화면도 관찰했다. 글자 크기로 Activity가 다시 열린 뒤에는 회색으로 표시됐다.
- iOS에서 이미 열린 카드의 글자 크기를 `large`에서 `accessibility-extra-extra-extra-large`로 바꾸면 본문과 버튼 글자가 잘렸다. 최대 크기를 적용한 뒤 새로 연 화면의 버튼과 생성 문구는 두 줄로 표시됐다. 실시간 글자 크기 변경은 미통과다. Android `font_scale=2.0`에서 새로 만든 카드 본문과 버튼은 읽을 수 있었지만 `1화`가 두 줄로 갈라지고 더하기 표시가 일부 잘렸다.
- 이 worktree의 API 프로세스만 중지해 연결 실패를 만들었다. iOS와 Android에서 `스토리를 만들지 못했어요`와 `닫기`·`다시 시도`를 확인했다. Android에서는 닫은 뒤 같은 카드, 원래 버튼과 카드 뒤 안내가 돌아왔다. iOS는 알림 확인 후 개발 세션 재시작으로 화면이 초기화되어 닫기 뒤 복원은 직접 확인하지 못했다. 같은 카드의 재시도 성공과 표지만 실패하는 경로는 이번 실행에서 확인하지 않았다.
- 테스트 뒤 iOS 글자 크기 `large`, Android 글자 배율 `1.0`, 두 기기의 라이트 모드를 복원했다. 루트 `bun run dev ios android`로 API와 Metro를 복원했다. 사용자 기존 스토리와 기록은 삭제하지 않았다. iOS에 검증용 `커피 머신 매장`과 `카페 와이파이`가 추가됐다.
- 복원 중 Android가 빈 화면에 머물렀다. 앱 재실행만으로 돌아오지 않았지만 이 worktree의 Metro에서 번들을 다시 읽은 뒤 홈과 프로필이 열렸다. 원인은 확인하지 못했으며 제품 오류로 단정하지 않는다. 마지막에는 두 기기에서 로그아웃하고 `agent-device` 세션을 닫았다. API 3951과 Metro 8132는 실행 상태로 남겼다.
- 별도로 표현 교정 한 건이 실패했다. [후속 확인](../../../../docs/follow-ups/episode-correction-invalid-entry.md)에 입력과 API 오류를 남겼다. 런타임 오류가 전혀 없었다고 판정하지 않는다.

화면 근거는 [evidence 폴더](../../../../docs/follow-ups/evidence/story-creation-refinement/)에 있다. `flyn-story-episode2-memory.png`는 실제 기억 반영, `flyn-story-completed.png`는 완주, `flyn-story-card-largest-settled.png`는 글자 잘림, `flyn-android-failure-restored.png`는 실패 뒤 복원이다.

**결론**: 두 화 연결의 성공 경로와 주요 화면 동작은 확인했다. 인터뷰 품질, 실시간 글자 크기 변경과 위에 적은 미검증 경로가 남아 전체 완료는 아니다.
