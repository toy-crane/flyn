# 쓰기 규칙이 사는 자리

## 결정

- 데이터를 지키는 규칙은 데이터베이스가 소유한다. API 서버 코드나 모바일 앱
  코드에 두지 않는다.
- 규칙은 표현할 수 있는 가장 낮은 층에 적는다. 누가 어떤 행에 닿는지는 RLS
  정책이, 값의 모양은 테이블 제약과 외래키가 정한다.
- `security definer` 함수에는 여러 행이나 여러 테이블을 함께 봐야 판단할 수 있는
  규칙만 남긴다. 정책과 제약이 이미 하는 검사를 함수가 다시 하지 않는다.
- 테이블마다 쓰기 함수를 새로 만들지 않는다. 새 테이블은 정책과 제약으로
  시작하고, 함수는 위 조건에 해당할 때만 더한다.
- 클라이언트가 부르는 함수는 공개 API로 다룬다. `authenticated`에 EXECUTE를 준
  함수는 앱을 거치지 않고도 호출된다는 전제로 설계한다.

## 경계

- 이 계약은 규칙이 어디 적히는지를 정하고, 각 기능의 규칙이 무엇인지는 정하지
  않는다.
- API 서버에 실제 secret key를 주어 신뢰 경계로 삼는 방향은 이 계약의 범위가
  아니다. 그 변경은 [AI 서버 경계](ai-server-boundary.md)와
  [계정 삭제 서버 경계](account-deletion-server-boundary.md)를 함께 다시 여는
  일이다.
- 로그인한 사람이 자기 계정의 진행을 스스로 꾸미는 경로를 막을지는 아직 정하지
  않았다.
  [follow-up](../follow-ups/signed-in-user-can-record-episode-endings-without-playing.md)이
  그 질문을 들고 있다.
- 스키마 원본과 마이그레이션 생성 방식은
  [Supabase 스키마 작업 방식](supabase-schema-workflow.md)이 소유한다.

## 이유

API 서버는 [AI 서버 경계](ai-server-boundary.md)에 따라 실제 secret key를 갖지
않고 로그인 사용자의 access token으로 데이터베이스에 닿는다. 그래서 데이터베이스가
보기에 API 서버와 사용자의 직접 호출은 같은 `authenticated` 역할이고, 둘을 구별할
수단이 없다. 모바일 앱 번들에는 publishable key가 들어 있으므로 사용자는 언제든
Data API를 직접 부를 수 있다. 규칙을 서버 코드에 두면 그 경로에서 지켜지지 않는다.
앱에 두는 것은 애초에 선택지가 아니다. 앱은 사용자 손에 있고, 앱에만 있는 규칙은
규칙이 아니라 앱의 습관이다.

같은 규칙을 함수마다 복제하면 하나만 빠뜨려도 그 경로로 구멍이 난다. 정책과 제약은
어느 문으로 들어오든 한 번만 적혀 있어도 지켜지고, 새 테이블이 늘어나도 복제되지
않는다. 함수는 정책 한 줄로 표현할 수 없는 것에만 쓴다.

## 재검토 조건

- API 서버가 실제 secret key를 갖고 앱의 테이블 권한을 걷어내, 데이터베이스가
  서버와 사용자를 구별할 수 있게 될 때
- Supabase가 호출자를 구별할 다른 수단을 제공할 때
- 정책과 제약으로 표현할 수 없는 규칙이 늘어 함수가 다시 대부분을 차지할 때
- Data API 노출 범위가 바뀌어 클라이언트가 함수를 직접 부를 수 없게 될 때

## 계속 제외하는 대안

- 규칙을 API 서버 코드에 두기: 사용자가 서버를 우회해 같은 요청을 보낼 수 있어
  규칙이 지켜지지 않는다. 서버가 신뢰 경계가 될 때 재검토한다.
- 규칙을 모바일 앱에 두기: 앱은 사용자 손에 있다. 어떤 조건에서도 다시 검토하지
  않는다.
- 테이블마다 쓰기 함수를 두어 모든 검사를 그 안에서 하기: 같은 검사가 함수 수만큼
  복제되고, 새 테이블마다 복제가 늘어난다. 정책으로 표현할 수 없는 규칙이 대부분이
  될 때 재검토한다.
- 데이터베이스에서 JSON 스키마로 문서 구조까지 검증하기: 검증 규칙이 그 문서를
  만드는 라이브러리와 따로 움직여, 라이브러리를 올릴 때마다 두 곳을 고쳐야 한다.
  구조가 우리 것이고 오래 고정될 때 재검토한다.

## 보존할 근거

- 2026-08 로컬 스택에서 확인했다. 새 계정으로 로그인만 한 사람이 앱을 열지 않고
  `/rest/v1/rpc/finish_episode`를 직접 불러 자기 진행을 기록할 수 있었다. 함수로
  감싸는 것 자체는 호출자를 제한하지 않는다.
- 2026-08 조사에서 Supabase 공식 RLS 문서는 `security definer` 함수를 노출되지
  않은 스키마에 두고 클라이언트 역할에서 EXECUTE를 회수하라고 권한다. 앱이 직접
  부르는 RPC는 그 권고를 따를 수 없으므로, 그런 함수는 공개 API로 다룬다.
- 같은 문서는 정책에서 `auth.uid()`를 `(select auth.uid())`로 감싸라고 권한다.
  행마다 부르지 않고 문장마다 한 번 부른다.
