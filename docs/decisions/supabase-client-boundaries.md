# Supabase 클라이언트 경계

## 결정

- `@repo/supabase`를 모바일과 서버(`apps/api`)가 함께 사용하는 내부 패키지로 둔다.
- 공유 패키지는 Supabase 스키마에서 생성한 TypeScript 타입과 그 위에 얹는 좁힌 타입만 소유하는 타입 전용 패키지다.
- 생성 타입은 jsonb 열을 `Json`으로 내놓는다. 열에 담기는 구조를 알면 생성 파일을 고치지 않고 `type-fest`의 `MergeDeep`으로 좁힌 타입을 병합한다. 지금은 `episode_messages.parts`를 AI SDK의 `UIMessage["parts"]`로 좁힌다.
- 행 타입 헬퍼(`Tables`, `TablesInsert`, `TablesUpdate`)는 병합한 `Database` 위에서 다시 정의한다. 생성 파일의 같은 이름 헬퍼를 그대로 다시 내보내면 좁힌 타입이 헬퍼 경로에서 사라진다.
- 모바일 앱은 `createClient<Database>`로 싱글턴 클라이언트를 직접 만든다.
- 이 클라이언트는 `@supabase/supabase-js`, React Native URL polyfill과 Expo SQLite 기반 `localStorage`를 사용한다.
- 모바일 앱은 `EXPO_PUBLIC_SUPABASE_URL`과 `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`를 읽는다.
- 루트 개발 세션에서는 `EXPO_PUBLIC_DEV_SESSION_SUPABASE_PORT`로 만든 주소가 `EXPO_PUBLIC_SUPABASE_URL`보다 우선한다. 개발 세션 밖에서는 기존 URL을 그대로 사용한다.
- 템플릿 사용자는 README의 절차에 따라 로컬 스택의 출력 또는 원격 프로젝트 설정에서 공개 URL과 publishable key를 확인한다. 확인한 값은 `apps/mobile/.env.local`에 직접 설정한다.
- 초기 설정, 로컬 스택 시작과 모바일 실행 명령은 `apps/mobile/.env.local`을 생성하거나 덮어쓰지 않는다.
- 서버는 같은 스키마 타입을 사용하되, 서버 런타임의 환경 변수와 권한에 맞는 별도 클라이언트를 초기화한다.

## 경계

- 공유 패키지는 Supabase 런타임 SDK, Expo 또는 서버 전용 저장소를 의존성으로 갖거나 환경 변수를 직접 읽지 않는다. `ai`와 `type-fest`는 좁힌 타입을 만드는 데만 쓰며 `import type`으로만 가져온다.
- `apps/mobile/.env.local`은 Git에서 제외하고, 저장소에는 필요한 변수 이름만 보여주는 환경 변수 예시 파일을 둔다.
- 공유 패키지와 모바일 앱에는 `service_role` 또는 secret key를 포함하지 않는다.
- 이 결정은 클라이언트와 타입의 소유권만 정한다. 인증 화면과 세션 생명주기, 서버의 사용자 권한 전달 방식과 관리자 권한 사용 범위는 별도로 결정한다.

## 이유

스키마에서 생성한 타입은 동일한 Supabase API 계약을 표현하므로 모바일과 서버가 공유해야 한다. 반면 런타임 SDK, 세션 저장소, 환경 변수와 비밀 키는 실제로 클라이언트를 생성하는 소비자가 소유해야 한다. 타입 전용 패키지로 두면 스키마 계약 중복을 막을 수 있다. 클라이언트 생성은 런타임마다 저장소와 권한이 달라 공유 추상화를 미리 만들지 않는다. 환경 변수 파일을 자동으로 전환하려면 별도 명령과 상태가 필요하다. 로컬 실행이 사용자가 설정한 원격 값을 덮어쓸 수도 있다. 초기에는 짧은 수동 절차가 더 분명하고 안전하다.

jsonb 열에 무엇을 담는지도 스키마 계약의 일부다. 좁힌 타입이 없으면 저장과 조회 양쪽에서 타입을 강제로 바꿔치기하게 된다. 생성 파일을 고치지 않고 그 위에 병합하면 `bun run db:types`를 다시 실행해도 좁힌 타입이 남는다. part 구조를 데이터베이스에서 JSON 스키마로 검증하지는 않는다. 그 구조는 AI SDK가 판올림마다 바꾸는 계약이고, 런타임 검증은 SDK가 같은 버전으로 한다.

루트 개발 세션은 `.env.local`을 바꾸는 대신 세션 전용 URL을 자식 프로세스에만 넣는다. 이 값은 해당 실행이 끝나면 사라지므로 사용자가 선택한 일반 또는 원격 Supabase 설정을 보존한다.

## 재검토 조건

- Supabase가 모바일과 서버의 저장소 및 인증 문맥을 안전하게 추상화하는 공식 범용 어댑터를 제공할 때
- 모바일과 서버가 서로 다른 Supabase 프로젝트나 호환되지 않는 스키마를 사용하게 될 때
- 둘 이상의 런타임에서 안전하게 공유해야 하는 실질적인 클라이언트 생성 로직이 반복될 때

## 계속 제외하는 대안

- 타입이 지정된 클라이언트 팩터리를 공유 패키지에 미리 추가: 현재는 `createClient<Database>` 한 줄만 감싸며, 모바일과 서버의 서로 다른 초기화를 한곳에 묶는 추상화가 된다. 둘 이상의 런타임에서 공유할 실질적인 초기화 규칙이 생길 때 재검토한다.
- 완성된 싱글턴 클라이언트를 공유 패키지에서 `export`: Expo 저장소와 공개 환경 변수 또는 서버 비밀 키가 하나의 초기화 경로에 섞인다. 모든 소비자가 같은 런타임과 권한 문맥을 갖게 될 때만 재검토한다.
- Supabase 타입과 클라이언트를 모바일 앱에만 배치: 서버가 같은 스키마 계약을 중복 생성하고 관리하게 된다.
- `db:start`가 로컬 접속 정보를 자동 주입하거나 환경 변수 파일을 갱신: 원격 설정을 덮어쓸 수 있고 환경 선택을 위한 추가 상태와 명령이 생긴다. 로컬과 원격을 자주 전환해 수동 설정 오류가 실제 문제로 확인될 때만 재검토한다.
