# 프로필 identity와 온보딩 상태

## Decisions

- `public.profiles`는 `auth.users.id`와 같은 기본키를 쓰는 1:1 계정 정보다. Auth
  사용자 생성 trigger가 같은 경계에서 행을 만들며, 세션 뒤 행이 없으면 온보딩이
  아니라 데이터 무결성 오류다.
- 이메일의 원본은 Auth이고 본인에게만 보인다. 프로필에서 사용자가 직접 정하고
  남에게 보이는 값은 닉네임인 `display_name`과 아이디인 `username`이다.
- 닉네임은 사람이 읽는 이름이다. 중복은 허용하지만 이모지와 장식용 기호는
  허용하지 않는다. provider 이름은 입력 후보일 뿐이며 사용자의 확인 없이
  저장하거나 로그인 때 덮어쓰지 않는다.
- 아이디는 남이 사용자를 찾을 때 입력하는 공개 고유 키이며 로그인 자격증명이
  아니다. 영문 소문자·숫자·`_`·`.`만 쓰고, 처음과 끝은 영문 소문자나 숫자이며,
  연속 마침표를 허용하지 않는다.
- 닉네임과 아이디가 모두 채워져야 온보딩 완료다. 별도 완료 flag를 두지 않고
  비어 있는 첫 단계부터 다시 시작한다.
- 사용자는 RLS 안에서 자기 닉네임과 아이디만 수정한다. 아이디 가용성 함수는
  불리언만 반환하는 UX 보조 수단이고, 소문자 정규화 유니크 인덱스가 실제 보안
  경계다.

## Why

사람이 읽는 이름과 남이 찾아 입력하는 키는 중복 가능 여부가 반대라 한 필드가
겸할 수 없다. Auth 생성과 프로필 생성을 분리하지 않으면 세션은 있지만 프로필이
없는 상태와 불필요한 클라이언트 생성 권한이 생긴다. 완료 상태를 실제 필드에서
도출하면 별도 flag와 값이 어긋나지 않는다.

한국어 UI에서 `아이디`는 카카오톡·라인처럼 로그인 계정과 별개인 검색 키로도
익숙하다. `닉네임`은 고유 키가 아닌 사람이 읽는 이름을 `아이디`와 가장 분명하게
구분한다.

## Boundaries

- 로그인은 Apple·Google·이메일 OTP뿐이며 아이디 로그인은 범위 밖이다.
- 조회 실패, 프로필 행 없음, 닉네임이나 아이디가 비어 있는 상태는 서로 다르다.
- 아이디 가용성 응답은 존재 여부 외의 프로필 정보를 노출하지 않는다. 저장 순간의
  유니크 충돌은 일반 저장 실패가 아니라 중복 상태로 처리한다.
- 아이디로 사람을 찾는 화면, 공개 프로필 열람, 아바타와 bio는 이 계약이 선점하지
  않는다.
- 계정 삭제는 [계정 삭제 계약](no-apple-token-revocation.md)이 소유한다.
- 구현 범위와 남은 검증은
  [온보딩 스펙](../specs/onboarding-nickname-and-id/spec.md)이 소유한다.

## Reconsider when

아이디 검색 표면보다 온보딩이 훨씬 먼저 출시돼 사용자가 용도를 이해할 수 없거나,
공개 identity 요구가 바뀌거나, 닉네임 없이 완료할 수 있는 경로가 필요해지면 다시
정한다.

## Still-rejected alternatives

- 닉네임 하나를 고유 검색 키와 사람이 읽는 이름으로 함께 쓰기.
- 사용자 문구에 `표시 이름`, `사용자 이름`, `핸들`을 섞어 쓰기.
- 아이디를 로그인 자격증명으로 쓰기.
- 앱 첫 진입 때 클라이언트가 프로필을 만들기.
- `onboarding_completed`와 실제 필드 null 상태를 함께 유지하기.
- provider 이름이나 이메일 파생 아이디를 사용자 확인 없이 저장하기.

## Evidence worth preserving

- 카카오톡과 라인은 `아이디`를 로그인 계정과 별개인 고유 친구 검색 키로 쓴다.
- 아이디 문자 규칙은 카카오톡·인스타그램·디스코드의 공통분모를 택했다. 길이는
  4–20자이며 소문자 기준 중복 불가다.
- RLS 때문에 다른 사용자의 행을 직접 조회할 수 없으므로 가용성 확인에는 제한된
  `security definer` 함수가 필요하다. 경쟁 상태의 최종 방어선은 유니크 인덱스다.
