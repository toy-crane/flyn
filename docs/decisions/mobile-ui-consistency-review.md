# 모바일 UI 일관성 검토

## 결정

- 구현 에이전트와 검토 에이전트는 아래의 공통 기준을 모바일 UI 작성과 검토에 함께 적용한다. 개별 화면의 수치를 새로 정하는 규칙이 아니라, 같은 제품 역할에 같은 기준을 적용하고 반복되는 배치 오류를 확인하는 작업 기준이다.
- 모바일 UI 변경은 저장소 전용 `mobile-ui-consistency-reviewer`가 읽기 전용으로 검토할 수 있게 한다. 공용 검토 계약은 `.agents/reviewers/mobile-ui-consistency-reviewer.md` 한 곳에 둔다.
- Codex와 Claude Code는 같은 공용 검토 계약을 사용한다. 도구별 agent 파일은 읽기 전용 권한과 계약을 연결하는 얇은 실행 설정만 맡는다. 검토 계약은 일반 Skill로 제공하지 않는다.
- 검토 에이전트는 변경한 모바일 UI와 주변의 같은 역할을 가진 구현을 함께 읽는다. 결정 계약, 적용 중인 명세, 공용 컴포넌트 계약, 같은 역할의 기존 구현 순서로 근거를 판단한다.
- 직접 확인할 수 있는 프로젝트 규칙 위반만 `FINDINGS`에 남긴다. 취향에 따른 디자인 제안, 일반 코드 품질 문제와 현재 코드에 단순히 많이 보이는 방식은 UI 일관성 위반의 근거로 삼지 않는다.
- 실제 렌더링이 필요한 플랫폼, 화면 모드, Dynamic Type, 키보드, 애니메이션과 접근성 동작은 정적 검토로 통과했다고 판단하지 않는다. 실행 증거가 없으면 `UNVERIFIED`로 분리한다.

### 작성과 검토의 공통 기준

1. **같은 역할의 조합을 먼저 찾는다.** 변경 전에 해당 결정 계약, 공통 컴포넌트와
   같은 역할의 화면을 확인한다. 글자, 아이콘, 진행 표시를 각각 재사용하는 데서
   끝내지 않고 함께 놓인 조합의 크기, 간격, 정렬과 상태 변화까지 비교한다.
   기존 코드에 많이 쓰였다는 이유만으로 올바른 기준이라고 판단하지 않는다.
2. **크기와 간격의 기준을 명시한다.** 같은 역할에는 같은 공통 토큰과 배치 규칙을
   적용한다. 기본 컴포넌트를 썼다는 이유만으로 주변 문구와 비율이 맞는다고 판단하지
   않는다. 화면마다 임의의 수치나 위치 보정을 추가하기 전에 조합의 공통 기준이
   맞는지 확인한다. 새로운 수치 제안을 사용자가 확정한 결정처럼 기록하지 않는다.
3. **표시 영역과 터치 영역을 구분한다.** 문구와 아이콘의 간격은 문구 영역과 표시
   영역 사이에서 확인한다. 터치 영역의 안쪽 여백이 시각적인 간격에 더해지는지
   확인하고, 간격 문제를 고치려고 누를 수 있는 영역을 줄이지 않는다. 실제 터치가
   가능한 범위와 이웃한 컨트롤의 입력도 확인한다.
4. **상태가 바뀌어도 같은 동작의 자리를 유지한다.** 기본, 로딩, 비활성, 실패와
   재시도 중 해당 UI에 있는 상태를 함께 확인한다. 아이콘을 스피너로 교체하는
   일만으로 문구 위치, 컨트롤 크기, 표시 영역과 간격이 바뀌지 않게 한다.
   자세한 진행 표시 기준은 [모바일 작업 진행 표시](mobile-action-progress.md)를 따른다.
5. **높이를 누가 차지하는지 확인한다.** 내용에 따라 늘어나는 영역은 일반 배치로
   공간을 차지하게 한다. 의도한 겹침이 있을 때만 화면 위에 겹쳐 놓고, 헤더,
   안전 영역, 키보드와 입력창의 공간을 중복 반영하지 않는다. 긴 문구나 큰 글자를
   고정 높이, 임의 말줄임이나 글자 축소로 숨기지 않고 해당 기능의 표시 계약을 따른다.
6. **실제 조합과 변화를 확인한다.** 변경이 영향을 주는 플랫폼에서 주변 문구와
   컨트롤을 포함한 화면을 확인한다. 크기와 간격 변경은 기본 글자와 큰 글자,
   한 줄과 여러 줄을 비교한다. 배치 변경은 첫 진입, 내용이 준비된 뒤와 재진입을,
   스크롤과 입력 변경은 사용자 스크롤과 키보드 전환을 확인한다. 정적 이미지 한 장이나
   특정 속성 값만 확인한 테스트로 동적인 배치까지 통과했다고 판단하지 않는다.

### 반복 오류의 확인 기준

| 발견한 문제 | 에이전트가 확인할 것 |
| --- | --- |
| 작은 문구 옆의 스피너만 크게 보임 | 문구와 표시가 같은 역할의 크기 기준을 쓰는지, 기본 스피너 크기를 문맥 없이 적용했는지 확인한다. |
| 간격 값을 줄였는데도 문구와 아이콘이 멀어 보임 | 표시 영역, 터치 영역과 각각의 안쪽 여백을 따로 확인한다. |
| 로딩으로 바뀔 때 문구나 버튼이 움직임 | 교체 전후의 표시 영역과 컨트롤 크기, 정렬 기준을 비교한다. |
| 첫 진입에만 내용이 겹치거나 가려짐 | 높이 측정 전후의 배치, 겹쳐 놓은 영역과 공간 보정의 중복, 목록의 위치 유지 동작을 확인한다. |
| 공통 컴포넌트를 썼는데 화면마다 다름 | 컴포넌트 주변의 문구 역할, 간격, 컨테이너와 상태 조합까지 비교한다. |

## 경계

- 검토 에이전트는 파일을 고치거나 앱을 실행하지 않는다. 일반 코드 리뷰, 타입 검사, 정적 검사, 자동 테스트와 `agent-device` 검증을 대신하지 않는다.
- 검토 에이전트는 새 디자인을 만들거나 화면 전체를 다시 설계하지 않는다. 확정된 규칙과 현재 변경 사이의 차이만 검토한다.
- 이번 결정은 기존 PR 코드 리뷰 워크플로를 바꾸거나 전용 검토 에이전트의 CI 자동 실행을 확정하지 않는다. 자동 실행은 실제 검토 결과와 비용을 확인한 뒤 별도로 정한다.
- 이 문서는 작성과 검토의 기준을 소유한다. 구체적인 크기, 색, 문구와 동작은 해당
  주제의 결정 계약과 공통 토큰이 소유하며 이 문서에 복제하지 않는다. 구현 에이전트가
  화면 검증을 수행하고 증거를 남기며, 읽기 전용 검토 에이전트는 그 증거를 평가한다.

## 이유

모바일 UI 규칙에는 Uniwind의 고정값과 런타임 값, 렌더러 소유권, 플랫폼별 아이콘과 접근성처럼 문맥을 읽어야 하는 예외가 많다. 단순한 문자열 검사나 inline `style` 개수는 허용한 구현까지 오류로 잡는다. 전용 검토 에이전트가 관련 결정 계약과 같은 역할의 구현을 함께 읽으면 이런 예외를 지키면서도 새 화면이 기존 규칙에서 벗어나는 일을 찾을 수 있다.

정적 검토와 실제 화면 검증을 분리하면 코드에서 증명한 문제와 기기에서 확인해야 할 위험을 섞지 않는다. 같은 공용 검토 계약을 Codex와 Claude Code에 연결하면 도구별 검토 기준도 갈라지지 않는다. 전용 agent로만 실행하면 구현 대화의 판단을 검토 맥락에 그대로 넣지 않는다.

컴포넌트 하나가 공통이어도 주변 문구, 터치 영역과 배치가 다르면 제품은 일관되지
않게 보인다. 조합과 상태 변화까지 같은 기준으로 확인하면 화면마다 수치를 다시
고르는 일을 줄이고, 스피너 비율, 과도한 간격과 첫 진입 겹침 같은 오류를 구현
단계에서 찾을 수 있다.

## 재검토 조건

- 반복되는 finding을 낮은 오탐률의 정적 검사로 확실하게 판정할 수 있게 된다.
- UI 변경 PR에서 같은 누락이 반복되어 전용 검토 에이전트의 자동 실행이 비용보다 더 큰 이점을 만든다.
- 정적 검토와 기기 검증을 나눈 방식 때문에 중요한 UI 문제가 반복해서 빠진다.
- Codex나 Claude Code의 agent 설정이 공용 검토 계약을 직접 읽을 수 없게 바뀐다.

## 계속 제외하는 대안

- 모든 UI 규칙을 lint로 강제: 런타임 값과 네이티브 경계처럼 코드 문맥이 필요한 예외에서 거짓 경고가 생긴다. 반복 finding 가운데 기계적으로 판정할 수 있는 규칙이 확인되면 그 규칙만 옮긴다.
- 검토 에이전트가 직접 앱을 실행해 화면까지 판정: 읽기 전용 검토와 실행 환경 관리가 섞이고 플랫폼별 증거가 없는 상태에서 통과로 오해할 수 있다. 실제 화면은 기존 `agent-device` 절차로 따로 확인한다.
- 기존 화면과 다르면 모두 finding으로 처리: 현재 구현의 우연한 차이와 확정된 제품 규칙을 구분하지 못한다. 같은 제품 역할과 근거가 확인된 차이만 다룬다.
- 증상마다 화면 전용 수치나 위치 보정을 추가: 공통 역할, 조합과 공간 소유권의
  문제를 남겨 같은 오류가 다른 화면에서 반복될 수 있다. 공통 기준으로 해결할 수
  없는 기능 요구가 확인된 경우에만 그 기능의 계약에서 예외를 정한다.
- 검토 계약을 Skill로 제공: 구현 세션이 같은 대화 맥락에서 직접 검토를 실행할 수 있어 전용 reviewer의 맥락 분리를 보장하지 못한다.
