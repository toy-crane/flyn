# 데이터베이스 공통 필드

## 결정

- 앱이 관리하는 모든 테이블은 `created_at`, `updated_at`을 `timestamptz NOT NULL`로 갖는다. 연결 테이블과 처리 상태 테이블도 포함한다.
- DB가 생성 시각과 수정 시각을 기록한다. 생성 시 두 값은 같고, `created_at`은 이후 바꾸지 않는다. 값이 실제로 바뀔 때만 `updated_at`이 바뀐다. 같은 값을 다시 쓰는 요청은 수정 시각을 바꾸지 않는다.
- `saved_at`, `finished_at`, `last_user_message_at`, `occurred_at`처럼 특정 행동이나 사건의 시각은 공통 시각과 구분한다. 공통 열을 추가했다는 이유로 사건 시각을 삭제하거나 의미를 바꾸지 않는다.
- 사건 시각 열은 그 시각을 읽는 곳이 있고, 값이 행의 `created_at`과 달라질 수 있을 때만 둔다.
- 행이 사건과 같은 순간에 생기고 그 시각이 바뀌지 않으면 `created_at`을 사건 시각으로 읽는다. 회차 시작 시각이 이 경우다.
- 이름에서 `_at`은 시각을 뜻한다. 목록의 순서는 `position`, 배열 안의 0부터 시작하는 위치는 `_index`로 표현한다.

## 경계

- Supabase가 관리하는 `auth`, `storage` 등 내부 테이블에는 적용하지 않는다.
- 공통 시각은 모든 변경 이력을 보관하는 감사 로그가 아니다. 메시지 순서를 정하는 기존 시각 규칙도 바꾸지 않는다.
- 기존 데이터의 알 수 없는 과거 시각을 실제로 관찰한 시각처럼 만들지 않는다. 보완 기준과 한계는 해당 변경 명세에 남긴다.

## 이유

테이블마다 시각 열의 유무와 의미가 다르면 생성과 변경을 같은 기준으로 확인할 수 없다. 바뀌지 않는 데이터와 연결에도 두 열을 두는 비용을 받아들이고, 새 테이블에도 예외 없이 적용할 수 있는 규칙을 택한다. 사건 시각을 수정 시각으로 대신하면 책갈피나 내부 처리의 변경이 플레이 시각과 학습 기록까지 바꾼다.

2026-09-15 사용자가 읽는 곳이 없거나 `created_at`과 늘 같은 사건 시각을 두지 않기로 했다. 같은 사실을 두 이름으로 두면 어느 쪽을 읽을지 매번 확인해야 하고, 읽는 곳 없는 열은 어디에 쓰는지 다시 조사하게 만든다. 판정은 `username_locked_until`, `protected_until` 같은 다른 열이 이미 한다.

## 재검토 조건

- 실제 측정에서 공통 열의 저장 또는 갱신 비용이 문제가 될 때.
- 변경 이력 전체를 보존해야 하는 요구가 생길 때.
- 행을 사건보다 먼저 만들게 될 때. 예를 들어 회차를 첫 사용자 메시지 전에 만들면 회차 시작 시각을 따로 둔다.

## 보존할 근거

- 공통 시각 전환에서 기존 사건 시각이 있으면 그 값을 사용하고, 과거 시각을 알 수 없는 콘텐츠와 연결은 전환 시각으로 보완했다. 수정 이력이 없는 행의 초기 수정 시각은 생성 시각과 같다. 보완값으로 실제 과거 생성 통계를 복원할 수 없다. 보존 사례는 `supabase/upgrade-tests/20260914091349/`에 있다.
