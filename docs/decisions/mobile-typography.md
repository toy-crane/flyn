# 모바일 타이포그래피

## 결정

- 모바일 앱은 커스텀 폰트 파일을 번들하지 않고 각 플랫폼의 시스템 폰트 스택을 사용한다. iOS는 Apple 시스템 폰트의 기본 디자인을, Android는 Android 시스템 기본 폰트를 따른다.
- 텍스트 일관성의 기준은 글꼴 이름이나 고정 수치가 아니라 시맨틱 텍스트 역할이다. 글자 크기와 접근성 확대의 기준은 Apple의 `largeTitle`, `title2`, `body`, `headline`, `footnote`, `caption2` 같은 시맨틱 텍스트 스타일이다.
- 제품 용어에 맞춘 `screenTitle`, `control`, `tabLabel` 같은 역할 이름이 필요하면 대응하는 시맨틱 텍스트 스타일을 명시한다. 역할 집합과 예외는 실제 화면에 필요한 만큼만 추가한다.
- React Native UI는 공통 역할을 크기, 행간, 굵기와 `dynamicTypeRamp`에 매핑하되 `fontFamily`를 지정하지 않고 시스템 글자 크기 확대를 유지한다.
- 호스팅된 SwiftUI는 같은 공통 역할을 네이티브 `textStyle`과 굵기에 매핑하고 기본 글꼴 디자인을 유지한다. 네이티브 셸은 운영체제가 소유한 텍스트 위계와 기본 스타일을 유지한다.
- 렌더러 간 일관성은 픽셀과 글리프의 완전한 동일성이 아니라 같은 역할, 위계, 강조와 접근성 동작으로 판단한다.
- 코드 표시는 monospace를 사용하는 유일한 예외다. AI 채팅의 인라인 코드와 코드 블록은 시스템 monospace 글꼴(`Platform.select({ ios: "Menlo", default: "monospace" })`)을 코드 표시 컴포넌트 한 곳에서만 지정한다. 글자 크기 확대는 다른 텍스트와 똑같이 유지한다.
- 시스템 글자 크기는 앱을 시작할 때의 값을 따른다. 앱을 연 채 시스템 글자 크기를 바꾼 경우는 지원하지 않는다. 그 경우의 잘림이나 어긋난 배치는 결함으로 다루지 않고, 앱을 완전히 닫고 다시 시작했을 때 맞게 그려지면 통과다. 설정에서 돌아오는 것만으로는 앱이 다시 시작되지 않는다.
- 글자 크기 검증은 각 플랫폼의 최대 시스템 크기(iOS `accessibility-extra-extra-extra-large`, Android 200%)로 바꾼 뒤 앱을 완전히 닫고 다시 시작해서 한다. 스펙의 완료 기준도 이 크기와 절차를 전제한다. 앱을 연 채 크기를 바꿔 가며 확인한 결과는 증거로 삼지 않는다.
- 글자 배율이 바뀔 때 뷰를 다시 만드는 처치(`key={fontScale}` 같은 강제 재생성)는 두지 않는다.

## 경계

- `ui-rounded`, serif, monospace 또는 브랜드 폰트는 전역 기본값이 아니다. 특정 기능에 필요할 때만 별도 결정을 거쳐 해당 기능에서 사용한다.
- monospace 예외의 범위는 코드 표시다. 본문, 숫자 정렬 또는 다른 화면으로 넓히려면 별도 결정을 거친다.
- 탭 라벨처럼 공간이 제한된 UI 크롬은 큰 접근성 글자 크기에서 실제 레이아웃을 검증한 뒤 해당 요소에만 확대 제한을 둘 수 있다. 본문과 주요 콘텐츠에 전역 제한을 적용하지 않는다.
- 텍스트 색상과 정렬은 이 결정의 범위가 아니다. 컴포넌트가 바꿀 수 있지만 텍스트 역할의 크기, 행간과 굵기 위계를 훼손하지 않아야 한다.

## 이유

시스템 폰트와 시맨틱 텍스트 스타일을 함께 사용하면 React Native UI, 호스팅된 SwiftUI와 네이티브 셸이 각 렌더러의 네이티브 동작을 유지하면서 동일한 정보 위계를 표현할 수 있다. 운영체제의 언어별 폰트 선택과 Dynamic Type을 보존하고, 커스텀 폰트 로딩과 굵기별 글꼴 파일 관리도 피한다.

앱을 연 채 바꾸는 경우를 지원하지 않는 이유는 그 경우만 빼면 상한 없이도 화면이 그대로 통과하기 때문이다. React Native는 글자 크기와 줄 높이를 같은 배율로 키우고, HeroUI Native도 상한 없이 이 기본값을 따르므로 앱을 완전히 닫고 다시 시작한 화면은 최대 크기에서도 손질 없이 그려진다. iOS 탐색 화면에서 확인했고, 나머지 화면과 Android는 스펙의 완료 기준이 확인한다. 반면 앱을 연 채 바꾸면 React Native가 글자만 새 크기로 그리고 텍스트 상자는 이전 크기에 남긴다. 이는 앱 코드로 고칠 수 없는 프레임워크 동작이고, 화면마다 뷰를 강제로 다시 만드는 처치가 늘어나는 원인이었다. WCAG 1.4.4는 200% 확대에서 내용과 기능이 남아 있기를 요구할 뿐 실시간 반영을 요구하지 않는다.

코드는 글자 폭 정렬이 읽기 기능의 일부라 monospace가 필요하다. 시스템 monospace를 쓰면 폰트 파일을 번들하지 않고 플랫폼 관례를 유지한다.

## 재검토 조건

- 브랜드 정체성이 플랫폼별 시스템 폰트보다 동일한 전용 서체를 요구한다.
- 지원 플랫폼이나 렌더러가 필요한 시맨틱 역할 또는 접근성 확대를 표현하지 못한다.
- 한국어와 영어, 기본 및 접근성 글자 크기의 실제 화면 검증에서 역할 매핑이 읽기 위계나 레이아웃을 반복적으로 훼손한다.
- React Native가 앱을 연 채 바뀐 글자 배율로 텍스트를 다시 배치하게 되거나, 실제 사용자가 앱을 연 채 크기를 바꾼 뒤 잘림을 반복해서 보고한다.

## 계속 제외하는 대안

- 앱을 연 채 바꾼 배율에 맞춰 뷰를 강제로 다시 만드는 처치: 화면마다 같은 처치를 되풀이해야 하고 목록의 행 높이 기억이나 잰 높이 상태까지 함께 버려야 한다. React Native가 재배치를 지원하면 다시 본다.
- 전역 `maxFontSizeMultiplier` 상한: 검증은 가장 쉬워지지만 본문 확대를 막아 Apple의 기대와 이 계약의 본문 규칙에 어긋난다. 재시작 검증에서 상한 없이 통과하므로 필요가 없다.
- 검증 크기를 WCAG 1.4.4의 200%로 낮추기: Android는 최대가 200%라 차이가 없고, iOS는 재시작 뒤 최대 크기도 추가 비용 없이 통과하므로 낮출 이유가 없다. 최대 크기 검증이 화면마다 손질을 요구하기 시작하면 다시 본다.

## 보존할 근거

- 2026-09-11 iOS 시뮬레이터에서 확인했다. `accessibility-extra-extra-extra-large`로 설정하고 앱을 완전히 닫고 다시 시작하면 HeroUI `TagGroup` 칩과 스토리 행이 손질 없이 온전히 그려진다. 같은 화면에서 앱을 연 채 `large`로 내리거나 다시 올리면 글자만 바뀌고 상자는 이전 크기에 남는다. 이전에 "고정 줄 높이 때문"으로 적었던 잘림은 이 경우였다.
- React Native 0.86의 iOS `RCTAttributedTextUtils.mm`와 Android `TextAttributes.kt`는 `lineHeight`에 글자 배율을 곱한다. 고정 px 줄 높이는 잘림의 원인이 아니다.
- HeroUI Native 1.0.8은 글자 확대 상한을 두지 않는다. Provider의 `config.textProps.maxFontSizeMultiplier`로 HeroUI 컴포넌트 전체에 상한을 걸 수 있고 문서 예시는 1.5다. 자체 상한은 Avatar 안의 글자(1.4)와 InputOTP(1.6)뿐이다. 이 설정은 저장소가 직접 쓰는 RN `Text`에는 미치지 않는다.
