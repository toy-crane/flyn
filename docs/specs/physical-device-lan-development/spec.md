# 실기기 LAN 개발 세션

## 상태와 목적

2026-09-07에 LAN 자동 설정 방향과 iOS·Android 실기기 지원 범위를 확정했다. 이 문서는 구현 전 계약이며 런타임 검증 완료를 뜻하지 않는다.

개발자는 Mac과 같은 Wi-Fi에 있는 실제 iPhone 또는 Android 폰에서 Development Build를 열고, 주소를 매번 수정하지 않아도 현재 worktree의 코드와 서버로 개발할 수 있다. 앱의 사용자 기능과 PRODUCT.md의 제품 방향은 바꾸지 않는다.

## 확정한 범위

- 루트 `bun run dev` 개발 흐름에 실기기 LAN 연결을 추가한다. 기존 플랫폼 지정과 Simulator·Emulator 실행은 유지한다.
- 현재 Mac의 LAN 주소를 자동 선택한다. 자동 선택이 어렵거나 틀리면 개발자가 주소를 명시할 수 있다. 선택한 주소와 대상 worktree를 보여 준다.
- 실기기의 Metro, API, Supabase 연결이 모두 기기에서 접근 가능한 주소를 사용한다. Metro만 연결된 상태를 전체 기능의 성공으로 보고하지 않는다.
- 개발자가 `.env.local`을 매번 수정하지 않는다. 일반 환경 설정이 개발 세션의 주소를 다시 덮어쓰지 않아야 한다.
- IP 변경은 다음 개발 시작 때 반영한다. 실행 중 네트워크를 상시 감시해 자동 복구하는 기능은 만들지 않는다.
- 본인 실기기에서 코드를 수정하며 확인하는 로컬 개발을 다룬다. 외부 iOS 공유는 TestFlight 방향으로 구분하되 배포 설정은 이번 범위에 넣지 않는다.

## 개발자가 겪는 흐름

1. 개발자는 Mac과 폰을 같은 Wi-Fi에 연결하고, 로컬 Supabase를 준비한다.
2. 작업할 worktree에서 플랫폼과 실기기 연결을 명시해 개발 세션을 시작한다.
3. 개발 세션은 해당 worktree의 포트를 확보하고 LAN 주소를 선택한다. 주소를 정할 수 없으면 명시 방법을 안내한다.
4. 개발 세션은 Metro와 API를 준비하고 공용 Supabase의 응답을 확인한다. Mac 내부 확인과 실기기 도달 확인을 구분한다.
5. 개발자는 worktree와 목적지 주소가 표시된 연결 링크 또는 QR 코드로 설치된 Development Build를 연다.
6. 폰은 선택한 worktree의 코드와 API를 사용한다. 로그인, 데이터 조회와 이미지 요청은 폰에서 접근할 수 있는 주소로 나간다.
7. 다른 worktree를 확인할 때는 그 worktree의 연결을 명시적으로 선택한다. 다른 세션이 시작됐다는 이유만으로 현재 폰의 연결을 가로채지 않는다.
8. 종료는 해당 worktree의 서버만 중단한다. 실기기의 앱이나 데이터를 삭제하지 않는다.

## worktree와 기기 경계

- worktree 절대 경로에 따른 기존 slot, Metro·API 포트, 프로세스와 캐시 소유권을 유지한다.
- 여러 worktree가 같은 LAN IP를 사용해도 Metro와 API 포트는 분리한다. 다른 worktree의 서버를 재사용하거나 종료하지 않는다.
- Supabase는 기존처럼 공용이다. 개발 명령은 이를 시작·중지·초기화하지 않는다. 데이터와 스키마가 worktree 사이에서 공유됨을 안내한다.
- iOS Simulator, Android Emulator, 실제 iPhone, 실제 Android 폰이 각각 올바른 서버 주소를 받는다. 같은 worktree에 실기기를 연결해도 기존 가상 기기의 연결을 깨뜨리지 않는다.
- 실기기를 Simulator·Emulator의 풀에 넣거나 초기화 대상으로 다루지 않는다.

## 변경 가능한 가정

- 호환되는 Development Build의 최초 빌드·서명·설치는 사전 준비로 둔다. 이번 작업은 설치된 앱을 LAN 개발 세션에 연결하는 데 집중한다. 실기기용 자동 설치까지 필요한 경우 별도로 범위를 정한다.
- 같은 폰의 앱 하나에서 worktree를 번갈아 연다. 폰에 저장된 로그인 상태와 앱 데이터는 worktree별로 분리하지 않는다. 이 부분은 별도 확인을 받지 않은 가정이며 완전한 격리가 필요하면 앱 설치 구조를 다시 결정한다.
- 실기기 선택 및 수동 주소 지정의 정확한 CLI 표기는 구현 시 정한다. 기존 명령의 의미는 유지하고 도움말에 새 흐름을 명시한다.
- 주소가 여러 개여서 확실하게 고를 수 없으면 임의의 주소로 성공을 보고하지 않고 수동 지정 방법을 안내한다.

## 수락 기준

### 주소와 개발 세션

- 같은 Wi-Fi에서 iPhone과 Android 실기기 모두 환경 파일 수정 없이 선택한 worktree에 연결된다.
- 자동 선택한 주소와 명시한 주소를 각각 확인한다. 유효하지 않은 주소, LAN 주소 없음, 서버 중단은 실패한 연결과 다음 행동을 구분해 안내한다.
- Mac의 LAN IP를 바꾼 뒤 개발 명령을 다시 실행하면 새 연결 주소와 앱의 API·Supabase 주소가 함께 갱신된다.
- 환경 파일에 loopback 주소가 있어도 개발 세션이 선택한 주소가 실제 번들과 네트워크 요청에 적용된다.
- 서버와 주소가 같으면 기존 세션을 재사용한다. 주소 변경으로 다시 시작할 때 다른 worktree의 프로세스와 데이터에 영향을 주지 않는다.

### 실제 기능

- iPhone과 Android 실기기에서 이메일 인증 코드 요청·확인·로그아웃을 실제 화면으로 완료한다. 로컬 인증 코드는 기존 `auth:otp` 경로로 확인한다.
- iPhone은 Google·Apple 로그인, Android는 Google 로그인을 실제 화면으로 확인한다. Android에 Apple 로그인을 추가하지 않는다.
- 인증 후 실제 API를 사용하는 기능을 실행하고 선택한 worktree의 API가 요청을 받았다는 근거를 남긴다.
- 두 실기기에서 스토리 표지, 기존 업로드 프로필 사진, 제공자가 준 프로필 사진을 각각 확인한다.
- 두 실기기에서 새 프로필 사진을 올리고 앱을 다시 열어 사진이 유지되는지 확인한다. 캐시된 사진만으로 다운로드 성공을 판단하지 않는다.
- 이미지 요청의 최종 URL과 실패 응답을 확인한다. 과거 Android 사진 문제의 원인은 아직 확인되지 않았으므로 주소 문제로 단정하지 않는다.
- Development Build의 HTTP 허용과 실제 OS·대상 SDK에 필요한 로컬 네트워크 권한을 확인한다. 로컬 개발 지원을 위해 배포용 앱의 네트워크 정책을 일괄 완화하지 않는다.

### worktree와 기존 기기

- 두 worktree를 동시에 실행하고, 실기기에서 A → B → A로 전환한다. 각 전환에서 코드, API 요청, 이미지 URL이 의도한 세션을 사용하는지 확인한다.
- 한 worktree를 종료한 뒤 다른 worktree는 계속 동작한다. 실기기의 설치 앱과 로그인 데이터를 지우지 않는다.
- iOS Simulator와 Android Emulator에서 기존 로그인·API·사진 표시가 유지된다.
- 같은 worktree의 가상 기기와 실기기를 함께 연결해도 각각 정상 동작한다.
- 실제 기기 종류, OS, 사용한 Development Build, worktree, 주소, 검증한 기능과 실패를 기록한다. 실기기가 없어 수행하지 못한 검증은 미검증으로 남기고 완료로 처리하지 않는다.

## 제외와 남은 위험

- Tailscale, 공개 터널, 원격 개발 서버, TestFlight 배포 자동화는 제외한다. 같은 Wi-Fi의 LAN 개발만 다룬다.
- worktree별 Supabase와 별도 앱 식별자를 통한 로그인 격리는 제외한다.
- 공유기의 기기 간 통신 차단, Mac 방화벽, OS 권한은 같은 Wi-Fi에서도 연결을 막을 수 있다. Mac에서 서버가 응답한다는 사실만으로 폰의 접근을 보장하지 않는다.
- 실기기와 가상 기기의 빌드 호환성은 플랫폼 이름만으로 보장하지 않는다. 호환되지 않는 앱의 재빌드·설치는 사전 준비 범위임을 안내한다.
- 이미지 로딩에서 별도 결함이 확인되면 근거를 남긴다. LAN 개발 경로를 막는 문제는 수락 기준을 충족하도록 해결하고, 관련 없는 화면 변경은 확대하지 않는다.
