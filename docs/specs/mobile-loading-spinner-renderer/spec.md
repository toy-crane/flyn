# 모바일 로딩 스피너 렌더러 명세

## 목표

- React Native UI에서 같은 뜻을 가진 회전 진행 표시가 한 가지 방식으로만
  그려지게 한다. 지금은 자리에 따라 두 컴포넌트로 갈려 있다.
- 각 플랫폼에서 그 운영체제의 진행 표시로 보이게 한다.
- 앱 화면 콘텐츠 위의 진행 표시가 언제나 앱이 정한 색으로 보이게 한다.
  플랫폼의 기본 색이 그대로 나오는 자리를 남기지 않는다.

## 확정 범위

- React Native UI의 회전 진행 표시는 React Native의 `ActivityIndicator`가
  그린다. HeroUI Native의 `Spinner`를 사용하지 않는다.
- 지금 `Spinner`를 쓰는 네 자리를 옮긴다. 인증 코드 확인, 대화 불러오기,
  에피소드 마무리의 진행 저장은 문구 옆에 서고, 아이디 확인은 입력 필드의
  접미 자리에 문구 없이 홀로 선다.
- 크기는 `small`을 사용한다.
- 앱 화면 콘텐츠 위의 진행 표시는 색을 명시한다. 값을 넘기지 않는 자리를
  두지 않는다.
- 옮기는 네 자리의 색은 지금과 같은 `accent`를 유지한다.
- 네이티브 셸 안의 진행 표시는 셸이 정한 색을 따른다. 프로필 저장의 Android
  헤더는 지금처럼 헤더의 `tintColor`를, iOS 툴바는 툴바의 기본 색을 쓴다.
- 네 자리의 화면 읽기 구조를 같게 맞춘다. 감싸는 요소가 이름과 `progressbar`
  역할, `busy` 상태를 지니고 진행 표시 자체는 화면 읽기에서 숨는다. 지금은
  아이디 확인만 `busy` 상태와 자식 숨김이 없으므로 이 자리를 나머지 셋에
  맞춘다.
- 각 자리의 접근성 이름과 진행 표시를 띄우는 시점은 바꾸지 않는다.

## 확정 제약과 이유

- 렌더러를 `ActivityIndicator`로 고른 것은 사용자가 확정했다. 이 컴포넌트는
  각 플랫폼의 진행 표시를 그대로 쓰므로 Android에서는 Material 원호가,
  iOS에서는 스포크가 나온다. `Spinner`는 두 플랫폼에서 같은 SVG를 그려서 어느
  쪽에서도 그 운영체제의 진행 표시로 보이지 않는다. 이미 다섯 자리가
  `ActivityIndicator`이므로 통일하면 앱 안에서 같은 뜻이 같은 모양이 된다.
- 색을 반드시 명시하는 이유는 색을 넘기지 않으면 앱과 무관한 색이 나오기
  때문이다. Android는 벡터의 tint가 테마의 `colorAccent`를 가리키는데 Expo가
  만드는 앱 테마는 이 값을 정하지 않아 AppCompat 기본 teal이 나온다. iOS는
  React Native가 `#999999`를 넣어 화면 모드와 상관없이 같은 회색이 된다.
- Android 테마의 `colorAccent`를 정하는 방법은 쓰지 않는다. 이 값은 진행
  표시만이 아니라 AppCompat 컨트롤 전반의 색이라서 스피너 하나를 위해 앱
  전체의 색 경로를 바꾸게 된다. 참조 저장소 다섯 곳도 이 값을 정하지 않는다.
- 크기를 `small`로 두면 네 자리의 지금 배치가 흔들리지 않는다. 프레임은
  16px에서 20dp로 커지지만 실제로 그려지는 링의 지름은 14px에서 15dp라 거의
  같다.
- `@expo/ui` 화면과 채팅 답변 대기는 각자의 명세를 따른다. 이 명세는 그 둘을
  바꾸지 않는다.

## 수용 기준

- 모바일 앱 코드에 `heroui-native/spinner` import가 남아 있지 않다.
- 앱 화면 콘텐츠 위의 `ActivityIndicator`가 모두 색을 받는다. 네이티브 셸 안의
  진행 표시는 셸이 주는 색을 따르므로 여기에 해당하지 않는다.
- 네 자리 모두 진행 표시가 지금과 같은 자리에 같은 크기로 선다. 문구가 있는
  세 자리에서 문구가 밀리거나 줄 높이가 바뀌지 않고, 아이디 확인에서 입력
  필드의 높이가 바뀌지 않는다.
- Android에서 네 자리 모두 앱이 정한 색으로 보인다. AppCompat 기본 teal이
  보이지 않는다. Light와 Dark를 모두 확인한다.
- iOS에서 네 자리 모두 앱이 정한 색으로 보인다. `#999999` 회색이 보이지 않는다.
- VoiceOver와 TalkBack이 네 자리에서 지금과 같은 이름을 읽고 진행 중임을 함께
  알린다. 진행 표시가 이름 없는 별도 요소로 읽히지 않는다.
- 모바일의 기존 자동 검사와 타입 검사가 통과한다.

## 가정

- 네 자리의 색은 `accent`를 유지한다. 지금 값은 `Spinner`의 기본색을 그대로
  받은 것이라 이 파랑을 의도해서 골랐다는 근거가 코드에 남아 있지 않다. 실제
  기기에서 보고 파랑이 과하면 `muted`로 낮춘다. 어느 쪽을 고르든 색은
  명시하므로 수용 기준은 그대로 적용된다.

## 제외

- `@expo/ui` 화면의 진행 표시. `ActionProgress`가 iOS는 SwiftUI `ProgressView`,
  Android는 Compose `CircularProgressIndicator`로 그린다. 이 경계는
  [모바일 작업 진행 표시](../../decisions/mobile-action-progress.md)가 정한다.
- 채팅 답변 대기의 글자 shimmer. 스피너를 두지 않는 것이 이 자리의 결정이다.
- Android 앱 테마의 색 설정과 이를 위한 config plugin.
- 진행 표시를 띄우는 시점과 1초 지연 규칙. 지금 규칙을 그대로 둔다.
- 버튼과 컨트롤 안 진행 표시의 색. 지금 값을 그대로 둔다.

## 남은 위험

- 공통 `Button`의 진행 표시 슬롯은 16 × 16인데 `ActivityIndicator`의 `small`은
  20 × 20이다. 이 작업이 만드는 상태는 아니지만, 기기에서 넘침이 보이면 따로
  다뤄야 한다.
- Android 텍스트 입력의 커서와 선택 색도 같은 `colorAccent`에서 온다. 앱은
  `selectionColor`와 `cursorColor`를 어디에도 지정하지 않으므로 이 값들도
  AppCompat 기본색일 수 있다. 소스로 추정한 것이라 기기에서 봐야 확인된다.
  이 작업의 범위는 아니지만 스피너 색과 같은 뿌리다.
- 파랑이 화면에서 과한지는 기기에서 봐야 판단할 수 있다. 문구가 있는 세
  자리와 입력 필드 안에 홀로 서는 아이디 확인은 판단이 갈릴 수 있다.
