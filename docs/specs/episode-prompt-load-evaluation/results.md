# Luna 실험 결과

현재 방식에서 회의의 주인을 혼동하는 대사가 30회 중 10회 나왔다. 결말과 기록을
모두 빼고 대사만 요청해도 30회 중 6회 같은 오류가 나왔다. 이번 표본에서는
대사와 판정을 한 응답에 맡기는 것만으로 문제를 설명하기 어렵다.

## 확인한 범위

2026-09-14에 여섯 장면을 네 조건에서 다섯 번씩 실행했다. 총 120회이며
모두 `openai/gpt-5.6-luna`를 요청했다. 응답의 모델도 `gpt-5.6-luna`, 실제
제공자도 OpenAI였다. Gateway가 기록한 제공자 시도는 호출마다 한 번이었다.

코드 기준은 `286329c622770ab4b27bbd5d8f1586cd34d8e75d`다. 입력과 실험 설계는
모델 호출 전에 `895101b`로 고정했다. 설치된 AI SDK 7.0.58을 사용했다.
자세한 조건과 재현 한계는 [실행 전 설계](README.md)에 있다.

## 대사와 결말을 나눠 본 결과

| 조건 | 회의를 사용자 일정으로 바꿈 | 없는 사용자 출근 일정 추가 | 모호한 시간 언급 | 결말 종류가 기대와 일치 |
| --- | ---: | ---: | ---: | ---: |
| A 현재 방식 | 10/30 | 0/30 | 2/30 | 30/30 |
| B 선택·관계·질문·수준 기록 제거 | 6/30 | 3/30 | 0/30 | 29/30 |
| C 대사만 생성 | 6/30 | 2/30 | 1/30 | 판정 기능 없음 |
| D 기존 사실을 인물별로 정리 | 6/30 | 7/30 | 1/30 | 30/30 |

앞의 세 열은 서로 겹치지 않는다. 출근 일정 추가는 명시된 회의의 주인을 바꾼
오류와 구분했다. 모호한 시간 언급은 확정 오류에 합치지 않았다. 모든 비율은
서로 다른 장면 여섯 개의 반복 호출 수이며, 일반 사용자 오류율을 뜻하지 않는다.

JSON 형식, 허용한 등장인물 이름, 발화 한두 개 규칙은 120회 모두 통과했다.
호출 실패와 스트림 오류는 없었다. 형식 검사가 통과해도 대사의 사실 관계는 틀릴 수 있다.

### 1. 결말을 맞히면서 대사의 인물 사정을 틀린다

회의가 있는 사람은 Owen이다. 사용자가 휴대폰 결제를 마치고 Owen에게 기다려
줘서 고맙다고 하자 다음 대사가 나왔다.

> Owen: You are welcome. I hope you make your meeting on time.

현재 방식 `s1-owner-A-1`에서 나온 말이다. 같은 응답은 결말을 성공으로 판정하고
휴대폰 결제로 주문한 음료를 받았다고 정확하게 기록했다. 대사만 생성한
`s1-owner-C-2`에서도 똑같은 문장이 나왔다. C는 결말·기록 필드나 그 생성 지시가 없다.

이 두 출력은 [주요 사례](evidence/examples.json)에 원문 그대로 모았다.

### 2. 오류가 결제를 마친 뒤의 인사말에 집중됐다

| 장면 | 회의 주인 혼동 | 없는 출근 일정 추가 | 모호한 시간 언급 |
| --- | ---: | ---: | ---: |
| s1 폰 결제 완료 확인 | 9/20 | 3/20 | 2/20 |
| s2 두 사람에게 각각 요청 | 0/20 | 0/20 | 0/20 |
| s3 아직 폰을 대지 않고 방법 질문 | 0/20 | 0/20 | 0/20 |
| s4 원래 음료 수령 완료 | 11/20 | 3/20 | 0/20 |
| s5 대체 음료 수령 완료 | 8/20 | 6/20 | 2/20 |
| s6 주문 취소 후 작별 | 0/20 | 0/20 | 0/20 |

s2와 s3에서는 Mia가 결제를 안내하고 Owen이 기다림에 답했다. 아직 하지 않은
결제를 완료했다고 쓰는 오류도 관찰하지 못했다. 이 장면에서도 Owen에게 회의가
있다는 정보는 입력에 들어 있었다.

s6의 마지막 입력은 사용자가 직접 `Owen, I hope you get to your meeting on
time.`이라고 말한다. 이 장면에서 오류가 없었다는 사실은 최근 발화의 명시적인
상대 표시가 도움을 줄 가능성을 보여 준다. 다만 취소와 성공은 다른 장면이므로
상대 표시만의 효과를 입증하지 않는다.

검토한 표본에서는 결제의 진행 상태와 발화자의 이름보다 **마무리 인사에 누구의
일정을 붙이는지**가 더 자주 틀렸다. 내부 원인이나 모든 장면의 취약점까지 확인한
것은 아니다.

### 3. 정보를 정리하면 다른 표현으로 같은 문제가 남을 수 있다

D는 회의 혼동 6회에 더해 `I hope you get to work on time.`처럼 입력에 없는
사용자의 출근 일정을 7회 만들었다. 회의라는 단어가 줄었다고 역할 정보가
안정됐다고 볼 수 없다. D는 기존 사실의 순서와 제목만 바꾼 제한된 실험이다.

### 4. 작업을 줄였을 때 판정 오류도 한 번 나왔다

`s5-compromise-B-1`은 대체 음료를 현금으로 샀다는 결과를 정확히 쓰면서
`kind`를 성공으로 골랐다. 현재 대본의 기준은 음료 변경을 타협으로 분류한다.
현재 방식 A와 정보 정리 D에서는 이런 판정 오류를 관찰하지 못했다.

A와 D가 만든 결말 객체 40개, B의 결말 객체 20개를 별도로 읽었다. 결제 방법이나
회의의 주인이 바뀌는 명백한 기록 오류는 보지 못했다. 다만 A의
`s5-compromise-A-4.level`에는 금지한 단어인 `사용자`가 한 번 들어갔다.
관계 기록에는 `서로의 주문을 기억하는 단골 관계`처럼 직원과 손님의 역할을
흐리게 쓰는 표현도 있었다. 이를 결말 종류 오답에 합치지는 않았다.

## 가설에 대해 말할 수 있는 것

- 추가 기록이나 결말 출력을 제거하면 회의 주인 혼동의 횟수가 줄었다. 다만 없는
  출근 일정까지 합치면 A 10회, B 9회, C 8회, D 13회다. 장면마다 5회인 이번
  표본으로 어느 조건이 더 낫다고 확정하기 어렵다.
- C에서도 오류가 재현되므로, 대사와 판정을 분리하는 것만으로 역할 혼동이
  사라지지는 않는다. 대사 생성 자체가 인물별 사실을 유지하는지도 확인해야 한다.
- 모델 크기나 능력의 한계를 부정한 실험이 아니다. Luna만 사용했고, 작업 개수와
  프롬프트 길이·출력 형식이 함께 달라졌다. 이 결과를 다른 모델로 일반화하지 않는다.
- C에는 판정 기능이 없다. 분리된 판정과 기록 생성까지 포함한 총비용·전체 정확도는
  이번에 측정하지 않았다. 제품 구조를 바꿀 근거로 바로 사용하지 않는다.

다음 검증의 후보는 같은 Luna에서 회의의 주인을 명시하고, 같은 의미의 마지막
입력을 상대 이름이 있는 문장과 없는 문장으로 비교하는 것이다. 역할의 주인을
사용자로 바꾼 반대 사례도 있어야 단순히 회의 언급을 피하는 답을 개선으로
오인하지 않는다. 이 후속 실험과 제품 프롬프트 변경은 이번 결과에 포함하지 않는다.

## 시간과 비용

| 조건 | 첫 대사 중앙값 | 전체 응답 중앙값 | 전체 응답 p90 | 출력 토큰 합계 | Gateway 비용 합계 |
| --- | ---: | ---: | ---: | ---: | ---: |
| A | 1.68초 | 3.25초 | 5.22초 | 6,255 | $0.00939 |
| B | 2.08초 | 2.93초 | 3.81초 | 3,647 | $0.00609 |
| C | 1.91초 | 2.39초 | 2.93초 | 2,561 | $0.00467 |
| D | 2.05초 | 3.84초 | 5.34초 | 6,365 | $0.00954 |

전체 120회의 Gateway `cost` 합계는 **$0.02968858**다. 추정 단가를 곱한 값이
아니라 응답 메타데이터의 합계다. 반복 입력이 많아 입력 캐시를 많이 사용했다.
출력 토큰에는 제공자가 보고한 reasoning 토큰도 포함된다. 동시 요청 3개로 얻은
시간이므로 운영 앱의 속도로 일반화할 수 없다. 대사만 요청한 C는 전체 응답은
짧아졌지만 첫 대사 중앙값이 A보다 빨라지지는 않았다.
