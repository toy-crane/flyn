# 역할 혼동을 줄이는 방법 확인

## 확인할 질문

Luna가 인물별 일정을 읽지 못하는지, 읽은 사실을 대사로 옮길 때 틀리는지 나누어
확인한다. 이전 실험에서 대사만 요청해도 오류가 남았으므로 이번에는 모든 조건에서
대사·결말·기록 기능을 유지한다. 사용자가 2026-09-14에 프롬프트 문제인지 Luna의
한계인지 점검하고 싶다고 요청했다. 기존 Luna만 사용한다는 범위를 유지한다.

## 실행 전에 고정한 조건

| 조건 | 처리 방법 | 장면 출력 |
| --- | --- | --- |
| A | 현재 프롬프트 | 현재와 동일 |
| R | 현재 프롬프트에 사실의 주인과 대명사 규칙 추가 | 현재와 동일 |
| S | Luna가 먼저 일정을 읽고, R에 그 결과를 전달 | 현재와 동일 |

R은 특정 답이나 이름을 넣지 않고, I/my와 you/your가 가리키는 사람을 유지하고
없는 일정을 추측하지 않도록 요청한다. 질문에 필요한 사실을 인사말로 대신하지
말라는 지시도 포함한다. R은 단어 하나의 효과를 분리하는 실험이 아니다.
정확한 지시는 [cases.ts](reproduction/cases.ts)의 `roleRule`에 보존한다.

S의 첫 호출은 일정과 그 주인만 JSON으로 읽는다. 다음 호출에는 이 출력 그대로를
넣는다. 기대 정답으로 고치거나 대체하지 않는다. 기대 정답은 읽기 결과를 기계로
비교할 때만 사용한다. 따라서 S가 나아지면 실제 두 번 호출하는 방법의 후보가 된다.
이 추출은 모델이 출력의 품질을 채점하는 단계가 아니다.

장면 여덟 개를 조건마다 다섯 번 실행한다. 장면 생성 120회와 일정 읽기 40회,
총 160회다. 기존 결과와 합치지 않고 같은 실행의 A와 비교한다.

| 장면 | 확인하는 내용 |
| --- | --- |
| o1 | 이전 실험의 실제 오류 입력 |
| o2 | o1의 마지막 입력에 Owen의 회의를 다시 명시 |
| o3 | 사용자가 회의에 가야 하고 Owen에게는 일정이 없는 반대 사례 |
| o4 | 이름을 Elena/Noah로, 회의를 기차로 변경 |
| o5 | o1에 관련 없는 대화 여섯 왕복 추가 |
| o6 | 사용자의 회의 일정을 직접 물어 답을 요구 |
| o7 | Owen의 회의 일정을 직접 물어 답을 요구 |
| o8 | 사용자의 기차와 Owen의 회의를 모두 물어 답을 요구 |

o6~o8은 일정 언급을 피한 채 짧은 인사만 해서 통과할 수 없게 한다. o3/o6은
무대·도입·이전 재촉 대사에 남은 Owen의 급한 일정을 함께 고쳐 모순을 없앤다.
o2는 이미 알려진 사실의 주인을 다시 말하므로 이름 유무만의 효과를 재는 것은 아니다.

## 실행과 판단

- 같은 장면의 입력은 세 조건에서 같다. 새 응답을 다음 입력에 누적하지 않는다.
- 현재 서버 모델 설정을 읽고 Luna 이외의 설정이면 중단한다. 설치된 AI SDK
  7.0.58과 실제 구조화 스트림을 사용한다. sampling은 서버 기본값을 유지한다.
- 일정 읽기 40회를 먼저 실행한다. 이어서 장면 생성 순서를 SHA256으로 섞고
  동시에 3개씩 실행한다. S는 같은 장면·반복 번호의 읽기 결과를 받는다.
- 응답, 사용량, 첫 대사와 전체 시간을 저장한다. S의 두 단계 시간 합은 같은
  사용자 요청에서 측정한 실시간 지연이 아니므로 예상 합계로 구분한다.
- 조건을 가린 장면 120개를 읽고 사실 오류, 모호한 지시 대상, 필수 답 누락을
  구분한다. 사람의 독립 검토나 별도 채점 모델 결과로 부르지 않는다.
- 한 장면에서 얻은 오류를 줄여도 이름 변경·반대 사례·긴 입력에서 재현되는지
  확인한다. 5회 반복의 관찰을 일반 사용자 오류율이나 신뢰성 보증으로 쓰지 않는다.
- 읽기에서 맞고 생성에서 틀리면 두 작업 사이에 차이가 있다는 증거다. Luna의
  추론 능력 전체를 증명하거나 반박하는 것은 아니다. 프롬프트와 모델 능력은
  서로 배타적인 원인이 아니다. 다른 모델을 시험하지 않아 모델 간 성능 한계는
  확정할 수 없다.

[AI 프롬프트 평가](../../../decisions/ai-prompt-evaluation.md)를 따르며 제품 코드는
바꾸지 않는다. 실험 입력은 [manifest](data/manifest.json)에 고정한다. 공식 문서의
방법을 Luna의 성능 보증으로 취급하지 않고 실제 출력으로 확인한다.
명확한 지시와 반복 평가라는 출발점은 [OpenAI 프롬프트 지침](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-4.1)에서도 제시한다.

## 다시 실행하기

저장소 루트에서 실행한다. 기존 `apps/api/.env.local`의 Gateway 설정이 필요하다.
마지막 `run` 명령이 실제 모델을 호출한다.

```sh
role_scratch=$(mktemp -d /tmp/flyn-role-check.XXXXXX)
cp docs/specs/episode-prompt-load-evaluation/role-check/reproduction/*.ts "$role_scratch/"
ln -s "$PWD/apps/api/src" "$role_scratch/src"
ln -s "$PWD/apps/api/node_modules" "$role_scratch/node_modules"
bun --cwd apps/api "$role_scratch/run.ts" prepare
bun --cwd apps/api "$role_scratch/run.ts" run
```

`prepare`는 모델을 부르지 않는다. 실행을 시작한 manifest는 다시 쓰지 않으며,
`run`은 이미 기록한 호출을 건너뛴다. 입력이 달라지거나 S에 필요한 추출이
실패하면 정답을 넣는 대신 중단한다.
