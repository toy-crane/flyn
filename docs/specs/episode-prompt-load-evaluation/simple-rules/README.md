# 쉬운 네 가지 규칙 비교

실행 결과는 [네 가지 규칙을 추가한 결과](results.md)에 있다.

사용자가 2026-09-14에 합의한 네 가지 규칙을 추가하고 Luna로 시험하도록 요청했다.
실험 당시 로컬 서버의 `episodeSystemPrompt` 끝에 다음 내용을 추가했다.
PR #111의 리뷰에서 품질 관문 미통과가 지적되어 병합 전에 후보를
`apps/api/eval/role-ownership-candidate.ts`로 옮겼다. 후보 내용은 같고 운영 프롬프트는
기존 버전을 유지한다. 아래 입력과 결과는 실험 당시 그대로 보존한다.

- 각 사람에게 어떤 일이 있는지 구분한다. 다른 사람에게 전해 말해도 그 일이 상대방의 일로 바뀌면 안 된다.
- 말하지 않은 사정을 만들지 않는다. 마무리 인사에도 같은 규칙을 적용한다.
- 말을 듣는 사람이 바뀌면 이름을 부르는 등 상대가 바뀐 것을 알린다.
- 이미 나온 정보로 질문에 답한다. 이미 아는 내용을 모르겠다고 하거나 인사말로 대신하지 않는다.

## 실행 전에 고정한 조건

[입력 전문](data/manifest.json)에 두 프롬프트와 메시지, 인물별 일정, 결말 기대값을 보존한다.
변경 전 프롬프트는 앞선 실험의 원본이다. 13개 장면 모두 변경 전후의 차이가
같은 네 규칙 블록을 덧붙인 것뿐임을 모델 호출 전에 확인했다.

앞선 역할 비교의 여덟 장면(o1~o8)에 결제 대기, 결제 전, 성공, 타협, 취소 장면
(s2~s6)을 더한다. 변경 전과 변경 후를 각각 다섯 번 실행한다.
총 130회이며, 이전 실행 결과와 합치지 않는다. 대사·결말·기록 기능은 모두 유지한다.
일정 읽기나 초안 수정 호출은 추가하지 않는다.

실행 순서를 SHA256으로 섞고 동시에 세 개씩 호출한다. 각 호출은 고정 대화에서
다음 응답 하나를 만든다. 새 응답을 이어 붙여 여러 차례 대화하는 실험은 아니다.
서버와 같은 모델 설정, 구조화 스트림, 기본 sampling과 AI SDK 재시도 설정을 쓴다.
Luna 이외의 모델 설정이면 중단한다.

## 확인할 내용

기계 검사는 스키마, 영어 대사, 화자, 발화 수, 결말 시점·종류와 특정 일정 오류
문구를 확인한다. 일정 문구 검사는 앞선 실제 오답을 떨어뜨리고 사용자가 회의에
가는 반대 사례를 통과시키는 자동 테스트로 판별력을 확인했다.
이 검사는 고정 장면에 한정하며 이름이 있는 줄은 따로 읽는다.

모든 응답은 조건을 가려 순서를 섞어 Codex가 읽고 관찰을 기록한다. 누구의 일인지
잘못 썼는지, 없는 일정을 만들었는지, 누구에게 말하는지 모호한지, 질문에 필요한
답을 빠뜨렸는지, 완료되지 않은 일을 완료했다고 했는지 살핀다.
사람의 독립 검토나 별도 채점 모델 결과로 부르지 않는다.

원문, parsed scene, 스트림, 모델, 사용량, 비용, 시간을 보존한다. 기계 검사에서
변경 후 답이 하나라도 실패하면 명령은 실패로 끝난다. 수치가 개선돼도 모든
검사를 통과한 것으로 표현하지 않는다. 다섯 번 반복과 같은 카페의 변형만으로
일반적인 오류율이나 Luna의 능력 한계를 확정하지 않는다.

## 다시 실행하기

저장소 루트에서 실행한다. 기존 `apps/api/.env.local`의 Gateway 설정이 필요하다.
`prepare`는 입력만 저장하고 `run`이 실제 모델을 호출한다.

```sh
role_scratch=$(mktemp -d /tmp/flyn-simple-rules.XXXXXX)
bun run --cwd apps/api eval:role-ownership prepare "$role_scratch"
bun run --cwd apps/api eval:role-ownership run "$role_scratch"
```

실행한 입력을 다시 쓰지 않고 이미 기록한 호출은 건너뛴다. 실행 도중 모델 설정이나
변경 후 프롬프트가 달라지면 중단한다. 재실행에서는 새 출력을 읽어 관찰해야 한다.
