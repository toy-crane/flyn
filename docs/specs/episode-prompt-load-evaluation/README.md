# Luna의 다중 인물 대화 문제 확인

## 목적과 범위

Luna가 대사, 결말 판정, 다음 화의 기록을 한 응답에서 만들 때 인물의 사정을
혼동하는지 확인한다. 사용자가 2026-09-14에 Luna만으로 현재 문제를 찾는
실험을 승인했다. 다른 모델과 제공자의 비교는 제외한다.

제품 프롬프트를 고치는 작업이 아니다. 실험은 저장소 밖의 scratch에서 실행하고
이 폴더에 설계, 실행 코드와 출력 전문을 보존한다. 상시 평가를 추가할 때는
[AI 프롬프트 평가](../../decisions/ai-prompt-evaluation.md)의 패키지별 명령을 따른다.
모델은 [AI 모델 라우팅](../../decisions/ai-model-routing.md)에 따라 서버 설정을
읽으며, 이번 실행은 `openai/gpt-5.6-luna` 이외의 설정이면 중단한다.

## 실행 전 고정한 설계

| 조건 | 한 응답에 요청하는 일 | 달라지는 부분 |
| --- | --- | --- |
| A 현재 방식 | 대사, 결말 종류·결과, 선택·관계·질문·영어 수준 | 현재 서버 프롬프트와 출력 형식 |
| B 추가 기록 제거 | 대사, 결말 종류·결과 | 네 기록의 지시와 출력 필드 제거 |
| C 대사만 | 대사 | 결말과 기록의 지시·출력 필드 제거. 사건의 성공·타협·실패 기준은 유지 |
| D 인물별 정보 정리 | A와 동일 | 무대의 기존 일곱 문장을 그대로 두고 항목별로 순서와 제목만 정리 |

대화 영어 수준을 조절하는 지시는 B와 C에도 남긴다. B에서 제거하는 `level`은
계정에 남기는 관찰 기록이다. 작업 개수, 프롬프트 길이와 출력 형식이 함께 바뀌므로
차이가 나더라도 작업 개수만이 원인이라고 단정하지 않는다.

다음 여섯 장면을 조건마다 다섯 번 실행한다. 총 120회다.

| 장면 | 확인할 문제 | 기대 결말 |
| --- | --- | --- |
| s1-owner | Owen의 회의가 사용자 일정으로 옮겨지는가 | 성공 |
| s2-addressee | Owen에게 기다려 달라는 요청과 Mia에게 결제 방법을 묻는 요청을 구분하는가 | 진행 중 |
| s3-not-done | 폰을 아직 대지 않았다는 말과 결제 방법 질문을 완료 행동으로 바꾸는가 | 진행 중 |
| s4-success | 폰 결제로 원래 음료를 받은 결과를 유지하는가 | 성공 |
| s5-compromise | 현금으로 대체 음료를 받은 결과를 성공으로 바꾸는가 | 타협 |
| s6-failure | 취소하고 음료 없이 떠난 결과를 성공으로 바꾸는가 | 실패 |

- 각 장면의 대화 기록과 마지막 입력은 네 조건에서 같다. 생성된 답을 다음 입력으로
  누적하지 않는다. 같은 입력의 반복은 서로 다른 사용자 5명의 표본이 아니다.
- 실제 [기기 대화 기록](../../follow-ups/evidence/multi-person-dialogue-role-confusion/multi-cast-runtime-dialogue.json)을
  사용한다. 당시 system과 이전 화의 기억 원문은 없으므로 현재 seed와 기억 없는
  프롬프트로 재구성한다. 전체 요청의 정확한 재현이라고 부르지 않는다.
- s1에는 앞서 관찰된 `Thanks, Owen. Your drink is ready...`라는 모호한 대사도
  그대로 남긴다. 기존 오류가 입력에 미치는 영향도 모든 조건에 동일하게 남는다.
- 순서는 고정 문자열과 호출 ID의 SHA256 값으로 섞는다. 동시 요청은 3개다.
- 설치된 AI SDK 7.0.58과 실제 `streamText`, 구조화 출력, 서버의 대사 스트림
  변환 함수를 사용한다. 앱·인증·DB 저장을 포함한 전체 경로 시험은 아니다.
- temperature, reasoning effort, 출력 토큰 상한은 서버처럼 별도로 지정하지 않는다.
  SDK 재시도는 이번 실험에서만 0회로 두고, 120초 제한과 실패 원문을 기록한다.
  Gateway 내부 재시도는 별도로 제어하지 않는다.
- D는 제한된 정보 배열 변경이다. D가 실패해도 모든 정보 구조 개선이 무효라는
  뜻은 아니다. C는 결말 기능이 없으므로 제품 대안의 완성도를 비교할 수 없다.

## 결과를 읽는 기준

1. 요청 실패, JSON 형식, 등장인물 이름, 발화 개수, 기대 결말은 기계로 검사한다.
2. 대사만 따로 모아 조건 이름을 가린 뒤 내용을 읽는다. 명백한 사실 오류와
   모호한 표현을 구분하고, 문제 문구와 이유를 기록한다. 사람의 독립 검토나
   별도 채점 모델을 실행한 것으로 표현하지 않는다.
3. 결말 기록은 별도로 읽고 선택·결제·일정의 주인이 유지되는지 확인한다.
   제거한 필드가 없다는 사실을 품질 개선으로 세지 않는다.
4. 조건별 분모, 장면별 오류, 첫 대사 시간, 전체 시간, 토큰과 비용을 함께 적는다.
   동시 요청과 캐시가 섞인 소표본 시간이므로 운영 지연의 확정치로 쓰지 않는다.
5. 현재 방식에서 오류가 재현되지 않으면 원인이 해결됐다고 결론 내리지 않는다.
   B나 C의 대사가 나아져도 별도 결말 생성까지 갖춘 제품 구조의 효과는 후속 검증이 필요하다.

실행 전 생성한 [manifest](evidence/primary/manifest.json)에 실제 대본, 대화,
모든 조건의 프롬프트·출력 스키마, SHA256, 호출 순서를 고정한다.
[preflight](evidence/primary/preflight.json)는 모델 설정, D의 사실 보존,
장면별 마지막 입력과 출력 필드 검사를 남긴다.

## 다시 실행하기

`apps/api/.env.local`에 기존 개발용 Gateway 설정이 필요하다. 아래 명령은 저장소
루트에서 실행한다. 마지막 `run` 명령이 실제 유료 모델을 호출한다.

```sh
eval_scratch=$(mktemp -d /tmp/flyn-prompt-load.XXXXXX)
cp docs/specs/episode-prompt-load-evaluation/reproduction/*.ts "$eval_scratch/"
ln -s "$PWD/apps/api/src" "$eval_scratch/src"
ln -s "$PWD/apps/api/node_modules" "$eval_scratch/node_modules"
bun --cwd apps/api "$eval_scratch/run.ts" prepare
bun --cwd apps/api "$eval_scratch/run.ts" run
```

`prepare`는 네트워크 모델 호출을 하지 않는다. `run`은 같은 출력 폴더에 이미
기록한 호출 ID를 건너뛴다. 실패한 호출도 재실행해 결과에서 지우지 않는다.
현재 소스에서 프롬프트나 스키마가 달라지면 고정한 실행을 중단한다. 과거 결과의
입력은 보존한 manifest가 기준이며, 같은 모델 ID도 제공자가 바꾸면 결과가 달라질 수 있다.
