# 다음 에피소드 제안 프롬프트 개선

## 상태와 목적

구현과 검증을 마쳤다. 2026-09-15 사용자가 범위를 프롬프트 개선으로 줄였다.
첫 사건 뒤에 다음 사건을 한 번 제안하는 흐름은 유지한다. 제안과 답변은 기존
채팅에서 글로 주고받는다.

플린이 자연스럽게 이어질 사건을 제안하여 사용자가 다음에 겪을 일을 떠올리도록
돕는다. 에피소드 수를 늘리는 것 자체를 목표로 삼지 않으며 하나로도 완성할 수 있다.

## 범위와 동작

### 첫 사건 뒤 제안

1. 첫 사건의 장소, 상대, 사건과 사용자가 하려는 일을 함께 정한다. 이미 충분히
   말한 내용은 다시 묻지 않는다.
2. 첫 사건이 정해지면 같은 스토리에서 이어질 구체적인 사건을 채팅으로 한 번
   제안한다. 지금 정한 에피소드만 만들어도 된다고 함께 안내한다.
3. 사용자는 기존 입력창으로 제안을 받아들이거나, 조건을 덧붙이거나, 다른 사건을
   말하거나, 추가하지 않겠다고 답한다. 정해진 문구나 번호로 답하도록 요구하지 않는다.
4. 추가하려는 사건이 충분히 구체적이면 카드를 낸다. 중요한 조건이 부족하면 그
   부분만 묻는다. 제안을 받아들이지 않은 상태를 합의로 간주하지 않는다.
5. 추가하지 않겠다고 답하면 지금까지 합의한 내용으로 카드를 낸다. 다음 사건을
   정한 뒤에도 추가 여부를 반복해서 묻지 않는다.

제안한 사건은 앞 사건의 성공, 화해나 도움을 전제로 삼지 않는다. 선택하지 않은
후보는 카드와 대본에 넣지 않는다. 사용자가 덧붙인 조건과 기존 사건은 보존한다.

### 바로 카드로 가는 경우

- 에피소드 하나만 원한다고 명시하면 추가 제안을 건너뛴다.
- `그냥 만들어 줘`처럼 더 묻지 말라고 하면 그때까지 들은 것으로 카드를 낸다.
- 처음부터 여러 상황을 요청하면 그 상황들을 먼저 정한 뒤 카드를 낸다. 그 사이에
  별도의 추가 제안을 끼워 넣지 않는다.
- 최대 5화에 도달하면 더 추가하는 제안을 하지 않는다.

### 카드 이후

기존 `에피소드 추가하기` 요청도 같은 프롬프트에서 처리한다. 추가 의사만 받으면
다음 사건을 글로 제안하고, 상황을 충분히 말했다면 바로 갱신한 카드를 낸다.
기존 사건과 합의한 조건은 보존한다. 대본 생성과 저장은 기존 카드의
`스토리 만들기`에서만 시작한다.

## 대화 예

아래 문장은 고정 템플릿이 아니다.

**사용자:** 해외 회사 첫 팀 회의에서 자기소개하고 싶어요. 경력직인데 영어가
서툴러서 긴장돼요.

**플린:** 이어서 점심시간에 동료와 친해지거나, 첫 업무에서 도움을 요청하는
상황도 해 볼까요? 자기소개 에피소드만 만들어도 좋아요.

**사용자:** 점심시간에 취미 이야기를 제가 먼저 꺼내고 싶어요.

플린은 합의한 두 사건의 카드를 낸다. `자기소개만 할게요`라고 답했다면
첫 사건만 담은 카드를 낸다.

## 완료 조건

- 충분한 첫 사건 뒤에는 바로 카드 대신 다음 사건을 글로 제안한다.
- 사용자의 동의 전에는 제안한 사건을 카드에 추가하지 않는다.
- 하나만 요청하거나 더 묻지 말라고 한 경우 추가 제안 없이 카드를 낸다.
- 추가 거절을 자연스러운 말로 답해도 재질문 없이 기존 사건의 카드를 낸다.
- 제안을 수락한 답, 다른 사건을 제안한 답, 조건을 덧붙인 답을 구분하고 보존한다.
- 추가 사건이 충분하면 바로 카드로 가고, 부족하면 필요한 조건만 묻는다.
- 추가 사건을 정한 뒤 또 다른 사건을 연달아 권하지 않는다.
- 처음부터 여러 상황을 요청하면 전부 정한 뒤 카드를 낸다.
- 5화 상한, 기존 사건 보존과 실제 결말을 미리 정하지 않는 규칙을 지킨다.
- `eval:story`에 새 흐름을 구별하는 사례와 검사를 추가한다. 수정 전 즉시 카드
  응답이 새 기준에서 실패하는지 확인하고 수정 후 반복 평가와 출력 전문을 남긴다.
- 기계 검사 외에 전문을 읽어 제안이 자연스럽고 간결한지, 사용자의 답을 제대로
  반영하는지 확인한다. 후보 개수나 문장 수만으로 품질을 판정하지 않는다.

## 남은 위험

- 모델이 제안을 동의로 간주하거나 추가 제안을 반복할 수 있다.
- 추가하지 않겠다는 답을 놓치거나 충분한 상황을 계속 되물을 수 있다.
- 후보 수는 고정하지 않는다. 자연스러운 사건이 하나뿐이면 억지로 늘리지 않는다.

## 구현과 검증 근거

2026-09-16, `creationSystemPrompt()`와 기존 `eval:story`만 바꿨다. 도구 스키마,
메시지 형식, 모바일 화면, 저장과 대본 생성 코드는 바꾸지 않았다. 선택지 시안은
`581b1b5`에서 삭제했다.

- 수정 전 비교: `apps/api`에서 `bun run eval:story --baseline --baseline-ref=581b1b5`.
  [29개 응답 중 4개 실패](../../../apps/api/eval/results/story-creation-baseline-1789484662257.md).
  충분한 첫 사건 뒤 즉시 카드와 짧은 수락 뒤 재질문을 새 검사가 구별했다.
- 수정 후: `apps/api`에서 `bun run eval:story`. 같은 서버 모델 설정
  `openai/gpt-5.6-luna`로 16개 대화, 회당 29개 응답을 3회 실행했다.
  [최종 실행은 87개 모두 통과](../../../apps/api/eval/results/story-creation-candidate-1789486831929.md)했다.
  프롬프트 SHA-256은 `3f18bdc5175a78ac9af3b1008e6858181bf986a990342fd2f03e468fff531d3b`다.
- 실패 기록도 보존한다. 초기 후보는 [5화 뒤 추가 제안 1개](../../../apps/api/eval/results/story-creation-candidate-1789485456947.md)를 냈다.
  최종 프롬프트도 앞선 [87개 중 외국어 조각 1개](../../../apps/api/eval/results/story-creation-candidate-1789486604149.md)가 있었고,
  [다음 실행](../../../apps/api/eval/results/story-creation-candidate-1789486693806.md)은 기계 통과 뒤 전문에서 다른 문자권 조각 1개를 찾았다.
  문자권 검사를 보완한 마지막 실행이 위 87개 통과다. 같은 최종 프롬프트의 세 실행을
  합치면 261개 중 2개가 실패했다. 마지막 통과를 항상 규칙을 지킨다는 보장으로 해석하지 않는다.
- 중간 평가에서 즉시 카드, 같은 사건 늘리기, 기존 화 수정, 결과 선확정과 관계없는
  외국어 조각을 관찰해 지시를 보완했다. 기계 검사는 카드 수와 기본 계약을 확인하며,
  선택 가능 안내의 정규식만으로 제안의 의미나 자연스러움을 판정하지 않는다.
- 마지막 3회 출력 전문에서 수락, 조건 추가(취미를 먼저 꺼내기·업무 제외), 다른 사건
  (양면 복사), 모호한 추가 의사와 자연스러운 거절을 확인했다. 선택하지 않은 점심을
  넣지 않았고, 충분한 답 뒤 다시 제안하지 않았다. 명시적 1화, 중단 요청, 최초 복수
  요청, 카드 이후 추가, 수정·삭제 시 다른 화 보존과 상한도 확인했다.
- `bun run test`, `bun run check-types`, `bun run check` 통과.
  API 340개 테스트와 모바일 734개 테스트를 포함한다. 평가 검사 단위 테스트 13개는
  안내 누락, 결과 결정 금지, 외국어 조각과 손에 든 소품을 실패에서 통과로 확인했다.
  소스 diff의 공백 검사도 통과했다. 출력 전문의 Markdown 줄바꿈용 끝 공백은 원문대로 보존했다.
- iOS `flyn-slot-1`: 첫 팀 회의 뒤 제안에 취미·업무 제외 조건으로 답해 2화 카드를
  만들고, 생성·두 화의 영어 대화·결말·표현 돌아보기·완주를 확인했다. 리뷰 전에는
  호텔 객실 변경 뒤 체크아웃 제안과 거절을 다시 확인했고, 객실 변경 1화만 남았다.
  긴 한국어 자동 입력 문제는 [별도 기록](../../follow-ups/ios-agent-korean-fill-truncation.md)에 남겼다.
- Android `flyn_dev_2`: 커피 머신 교환 제안 뒤 자연스러운 거절로 1화 카드를 확인했다.
  생성한 스토리에서 영어로 영수증·누수 영상·교환 의사를 전했고, 5턴 뒤 교환 성공과
  표현 돌아보기의 `마지막 이야기까지 함께했어요`를 확인했다.
- 런타임은 이 worktree의 API `3911`, Metro `8092`와 기존 Development Build를
  사용했다. 실제 로컬 이메일 코드 로그인으로 확인했으며 다른 worktree의 자원은 보존했다.
- 재현 중 API·Metro 로그와 기기의 React Native 오류·충돌 로그에서 관련 오류가
  없었다. iOS 세션 `prompt-ios`, Android 세션 `prompt-android`로 확인했다.
- Codex가 `581b1b5`부터 작업본까지 전체 구현 diff, 이 스펙, 연결한 결정 계약과
  평가 전문을 1회 리뷰했다. [리뷰 전 후보](../../../apps/api/eval/results/story-creation-candidate-1789485545794.md)의
  `실제 대화에서 정하지 않는다`라는 의미 반전 1종(P2)을 지적했다. details가 대본과
  첫 장면에 전달되는 코드까지 확인한 뒤, 실제 플레이가 결과를 정한다는 지시와 회귀
  검사를 추가했다. [첫 수정 평가](../../../apps/api/eval/results/story-creation-candidate-1789486370354.md)에서
  의미 반전은 사라졌으나 인물 설명의 외국어와 표지 소품을 발견해 기존 출력 규칙도 보완했다.
  최종 전문에서 이 세 문제의 재발은 없었다. 스킬 규칙대로 같은 범위를 다시 리뷰하지 않았다.
- 리뷰 수정 후 iOS `prompt-repair-ios`, Android `prompt-repair-android`에서 최종
  프롬프트로 비행기 사건을 새로 입력했다. 승무원 도움 제안을 거절하자 승객과의 1화만
  나왔다. 양쪽에서 각각 새로 생성하고 영어로 사정을 설명해 이해를 구했다. Emma가
  시간을 주겠다고 답하고 `해냈어요!`, 표현 확인, `마지막 이야기까지 함께했어요`가 나왔다.
  수정 후에도 결말을 실제 대화에서 정함을 확인했다. API·Metro에 관련 오류가 없었고
  양쪽 계정을 로그아웃한 뒤 기기 세션을 닫았다. 개발 서버는 켜 두었다.
