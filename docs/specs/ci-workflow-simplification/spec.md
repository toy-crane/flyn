# CI 워크플로 단순화

## 확정 범위

2026-09-10 대화에서 합의한 GitHub Actions 재구성을 확정한다. 검증과 배포를 한 워크플로로 합치고, 직접 만든 배포 상태 기록을 없애고, 변경 판정을 Turborepo 표준 명령에 맡기고, 문서만 바뀐 변경에는 검사를 돌리지 않는다. 배포 순서, 승인 게이트, 호환성 규칙 같은 배포 정책은 [검증과 내부 테스트 배포](../../decisions/continuous-delivery.md)가 정한 대로 유지한다. 이번 작업은 정책을 바꾸지 않고 그 정책을 실행하는 형태를 바꾼다.

## 사용자에게 보이는 결과

- 개발자는 워크플로 파일 하나에서 PR 검사부터 운영 배포까지 전체 순서를 읽을 수 있다.
- 문서만 바꾼 PR은 변경 판정 잡 하나만 돌고 필수 검사는 통과로 남는다. 합친 뒤에도 배포 잡이 뜨지 않는다.
- 코드 검사, 타입 검사, 테스트, DB 검사, fingerprint 라벨, 승인 대기, 배포 순서는 지금과 같은 결과를 낸다.
- 배포 이력은 저장소 첫 화면의 Deployments와 각 서비스의 대시보드에서 본다. 저장소 안의 상태 브랜치와 서명 키는 없어진다.
- 잡마다 반복하던 의존성 설치가 캐시를 타서 배포 한 번의 시간이 1분 안팎 줄어든다.

## 합의한 흐름

```text
ci.yml (PR과 main push 모두)
  changes: 기준 커밋 대비 영향 판정
    ├─ 영향 패키지 있음 → check · 타입 · 테스트
    └─ supabase/ 변경 → DB 검사
  Required validation · Required database validation (항상 실행, 건너뛰기와 실패 구분)
        ↓ main일 때만 needs로 이어짐
  plan → DB → Edge → API → 모바일 (영향 없는 서비스는 잡 자체가 뜨지 않음)

fingerprint.yml: PR마다 iOS fingerprint 계산 (변경 없음)
fingerprint-labels.yml: main 코드로 라벨만 씀 (main push와 fingerprint 완료 때)
claude.yml: @claude 멘션 응답 (변경 없음)
```

## 워크플로 구조

- `validate.yml`, `database.yml`, `deploy.yml`을 `ci.yml` 하나로 합친다. `deployment-access.yml`은 수동 읽기 검사로 남긴다.
- `fingerprint.yml`은 별도 워크플로로 둔다. PR 제목이나 base가 바뀔 때도 다시 계산해야 하고, 라벨 워크플로가 이 워크플로의 이름과 아티팩트를 보고 동작하며, 계약이 정한 권한 분리 구조에 속하기 때문이다.
- 배포 잡은 두 게이트 잡에 `needs`를 건다. 검사 통과 여부를 API로 조회하며 기다리는 코드는 없앤다.
- 게이트 잡 이름 `Required validation`과 `Required database validation`은 그대로 둔다. 브랜치 보호 설정을 바꾸지 않는다.
- 게이트 잡은 항상 실행하고, 선행 잡이 정당하게 건너뛰었을 때만 통과한다. 실패, 취소, 판정 잡 실패는 통과로 처리하지 않는다.
- 동시 실행 규칙은 워크플로 수준에 식으로 둔다. PR은 PR 번호별 그룹에 진행 중 취소를 허용하고, `main`은 운영 그룹에 취소 금지와 대기열을 둔다.
- `main`에 연달아 push하면 앞 실행이 검사와 배포를 끝낼 때까지 뒤 실행이 대기열에서 기다린 뒤, 자기 커밋의 변경만 배포한다. `main` 실행은 취소하지 않는다.
- `main` 배포 잡에만 `if`로 브랜치와 저장소를 확인한다. 뒤따르는 잡은 `needs`로 이어지므로 같은 조건을 반복하지 않는다.
- 승인 게이트는 지금처럼 GitHub Environments를 쓴다. `plan`이 판정한 환경 이름을 DB 잡과 Edge 잡에 붙인다. 승인이 필요한 잡은 이름에서 그 사실이 드러나게 한다.

## 변경 판정

- 기준 커밋은 PR이면 base 커밋, `main`이면 같은 워크플로의 마지막 성공한 `main` 실행의 커밋이다. 성공한 실행이 없으면 모든 서비스를 배포 대상으로 본다.
- 기준 커밋과 지금 커밋 사이의 영향 패키지는 `turbo query affected`로 뽑는다. `@repo/api`가 있으면 API 배포, `@repo/mobile`이 있으면 모바일 배포 대상이다. 공유 패키지와 루트 의존성의 영향은 이 명령이 판정한다.
- workspace 밖 경로는 따로 본다. `supabase/migrations`와 `supabase/config.toml`의 함수 설정은 DB와 Edge 대상이다. `.github/`, `scripts/`, 루트 설정이 바뀌면 전체 검사를 돌린다.
- 영향 패키지가 없고 위 경로도 바뀌지 않았으면 문서만 바뀐 것으로 본다. 검사 잡을 건너뛰고 게이트만 통과시키며 배포 잡을 만들지 않는다.
- 설치한 Turborepo 2.10.8로 확인했다. 문서만 바꾼 커밋은 영향 작업이 0개이고, `apps/api`만 바꾼 커밋은 `@repo/api`의 작업만 잡힌다. workspace 밖 경로는 이 명령이 보지 않으므로 경로 판정을 따로 둔다.
- checkout은 전체 이력을 받는다. 얕은 checkout이면 모든 패키지가 영향받은 것으로 잡힌다.

## 배포 상태

- 배포 상태 파일과 `deployment-state` 브랜치, HMAC 서명 키를 없앤다. 브랜치와 GitHub Secret 삭제는 상태 파일 없는 운영 배포가 한 번 성공한 뒤 사용자에게 확인하고 진행한다.
- 이미 올라간 것과 진행 중인 것은 각 서비스에 묻는다. Vercel은 배포 메타의 커밋과 요청 ID, Edge는 함수 소스에 새긴 커밋과 원격 설정, EAS는 실행의 커밋과 요청 ID, DB는 원격 마이그레이션 이력으로 확인한다.
- 서비스별 건너뛰기 판정은 그 서비스가 알려 준 현재 커밋을 기준으로 diff한다. 서비스가 커밋을 알려 주지 못하면 GitHub 실행 이력의 기준 커밋을 쓴다. 앞선 실행이 API에서 실패했어도 이미 올라간 Edge를 다시 배포하거나 다시 승인받지 않는다.
- 응답이 끊긴 뒤 다시 실행하면 같은 커밋과 요청 ID의 원격 작업을 찾아 이어받는다. 새 요청을 중복 생성하지 않는다.
- 이미 올라간 것보다 옛 커밋은 배포하지 않는다. 서비스가 알려 준 커밋과 지금 커밋의 조상 관계로 판정한다. 원격에만 있는 마이그레이션 버전을 만나면 실패로 멈춘다.
- 승인 판정은 `plan` 잡이 한다. 미적용 마이그레이션은 Supabase의 dry-run으로, Edge 함수 설정 변경은 기준 커밋과의 diff로 본다. 이를 위해 `plan`에 읽기용 Supabase 접근 토큰을 준다.
- 승인된 SQL 해시 검사는 그대로 남는다. PR에 해시를 넣어도 승인을 대신하지 못한다.

## 설치와 도구

- Bun 설치 캐시를 `bun.lock` 해시로 보존한다.
- `vercel`과 `eas-cli`는 배포 잡에서만 설치하고 버전으로 캐시한다. 둘을 루트 의존성에 넣어 PR 검사 잡의 설치 시간을 늘리지 않는다. 버전은 지금처럼 고정한다.
- 액션은 지금처럼 커밋 SHA로 고정한다.

## 라벨 게시

- `fingerprint-labels.yml`의 push 트리거를 `main`으로 좁힌다. PR은 `main`만 대상으로 열리므로 "base 브랜치에 새 커밋이 오면 라벨을 지운다"는 규칙을 그대로 지킨다.
- 라벨 계산은 PR마다 실행한다. 문서만 바뀐 PR에서도 계산하며, 이 결정은 아래 가정에 적는다.

## 범위 밖

- `claude.yml`과 CI 코드 리뷰 방식은 바꾸지 않는다. [CI 코드 리뷰](../../decisions/ci-code-review.md)가 정한다.
- 배포 순서, 승인 대상, 호환성 규칙, 모바일 배포 정책, 공개 출시는 바꾸지 않는다.
- fingerprint 라벨의 권한 분리 구조는 바꾸지 않는다. 라벨 쓰기는 계속 `main`의 코드만 실행한다.
- Android, 스테이징 환경, 외부 알림 채널은 다루지 않는다.

## 완료 조건

1. 정상 코드 PR은 check, 타입, 테스트, 두 게이트가 모두 통과한다. 잘못된 코드, 타입, 테스트를 넣은 PR은 해당 검사와 게이트가 실패한다.
2. 문서만 바꾼 PR은 변경 판정 잡과 fingerprint, 라벨 게시만 실행하고 두 게이트는 통과한다. 합친 뒤 배포 잡이 만들어지지 않는다.
3. `supabase/` 변경 PR은 DB 검사가 실행되고, 그 외 PR은 DB 검사가 건너뛰어지며 게이트는 통과한다. DB 검사 실패는 게이트 실패로 이어진다.
4. `main`에 합친 커밋의 배포 잡은 같은 실행의 게이트 뒤에 시작한다. 검사 결과를 API로 조회하는 코드가 저장소에 남지 않는다.
5. API만 바뀐 커밋은 API와 모바일 잡만 뜬다. 공유 패키지가 바뀐 커밋은 그 패키지를 쓰는 앱이 모두 대상이 된다.
6. 새 마이그레이션이나 Edge 함수 설정이 있는 커밋은 해당 잡이 `flyn-production-review`에서 승인을 기다린다. 그 외 커밋은 승인 없이 진행한다.
7. `deployment-state` 브랜치와 서명 키 없이 실제 운영 배포가 한 번 이상 성공한다. 같은 실행을 다시 실행하면 새 원격 작업이 생기지 않는다.
8. 앞선 배포가 실패한 뒤의 다음 배포는 마지막 성공 실행 이후의 변경을 모두 포함한다.
9. 설치 캐시가 적중한 잡의 설치 단계가 캐시 없는 실행보다 짧고, PR 검사 잡의 설치 시간은 지금보다 늘지 않는다. 캐시한 `vercel`과 `eas-cli`로 실제 배포가 성공한다.
12. 앞선 실행이 API에서 실패한 뒤 다음 실행은 이미 올라간 Edge를 건너뛰고 API부터 배포한다.
10. `fingerprint-labels.yml`이 `main`이 아닌 브랜치 push에는 뜨지 않고, `main` push 뒤 열린 PR의 이전 라벨을 지운다.
11. `scripts/ci`의 테스트가 새 워크플로 파일을 읽어 통과한다. 없어진 코드의 테스트도 함께 없어진다.

## 가정과 보류

- 가정: PR은 항상 `main`을 대상으로 연다. 다른 브랜치를 base로 쓰기 시작하면 라벨 워크플로의 트리거를 다시 넓힌다.
- 가정: fingerprint 계산은 문서만 바뀐 PR에서도 실행한다. 병렬이라 전체 시간에 영향이 없고, 건너뛰면 라벨 워크플로가 결과 없음을 새로 다뤄야 한다.
- 가정: 워크플로 수준 `concurrency`의 `group`과 `cancel-in-progress`에 식을 쓴다. `queue` 속성이 식과 함께 동작하지 않으면 `main` 실행의 대기열 없이 기본값으로 시작하고 그 사실을 기록한다.
- 가정: `eas-cli`를 저장소 밖에서 전역 설치하던 이유는 기록에 없다. 저장소 밖 설치는 유지하고 캐시만 더한다. 캐시 복원 뒤 실제 모바일 배포 한 번으로 확인한다.
- 보류: 문서만 바뀐 PR에서 fingerprint까지 건너뛰는 것은 라벨 워크플로 수정과 함께 별도로 정한다.
- 보류: CI 자동 코드 리뷰 도입은 별도 결정이다. 이 스펙은 `claude.yml`을 그대로 둔다.

## 남은 위험

- 이전 스펙 [내부 테스트 자동 배포](../continuous-delivery/spec.md)의 완료 조건과 기록 중 서명된 상태 기록에 기대는 부분은 이 스펙이 대체한다. 이전 스펙의 정리는 별도 문맥 정리 작업에서 한다.
- 마지막 성공 실행을 GitHub API에서 읽으므로 실행 이력이 지워지면 전체 배포로 되돌아간다. 각 서비스가 이미 올라간 커밋을 알려 주므로 중복 배포는 생기지 않는다.
- 새 워크플로의 첫 `main` 실행은 성공한 실행이 없어 모든 서비스를 대상으로 잡는다. 서비스가 알려 준 커밋으로 건너뛰지 못하는 서비스는 한 번 중복 배포될 수 있다. 첫 실행의 임시 동작으로 받아들인다.
- 게이트와 배포를 한 실행에 두면 `main` 실행 하나가 검사부터 모바일 배포까지 길어진다. 취소 금지와 대기열이 이를 감당해야 하며, 실제 연속 push로 확인한다.
- `plan`에 Supabase 읽기 토큰이 들어간다. 지금도 `deployment-access.yml`이 같은 토큰으로 읽기만 하며, `plan`은 쓰기 명령을 실행하지 않는다.
- 공식 문서는 구현 때 원본을 다시 읽는다. GitHub Actions 동시 실행과 필수 검사, Turborepo `query affected`, Supabase `db push`, Vercel 배포 메타, EAS Workflows 조회 API를 확인했다.
