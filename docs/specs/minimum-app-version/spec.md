# 최소 지원 앱 버전

## 목적과 확정한 범위

운영자가 Supabase Dashboard의 Table Editor에서 최소 지원 앱 버전을 조절한다. 앱은 이 값을 조회해 더 오래된 앱에 업데이트 화면을 보여 준다. 별도 관리자 화면, 특정 빌드 차단, 강제 OTA 재시작은 만들지 않는다.

[모바일 업데이트 경험](../../decisions/mobile-update-experience.md)은 일반 OTA의 무알림 적용과 최소 지원 버전 정책을 정한다. 제품의 영어 대화를 방해하지 않는 원칙은 루트 [PRODUCT.md](../../../PRODUCT.md)를 따른다.

## 운영자가 하는 일

- 최소 지원 버전에 `1.2.0`을 저장하면 설치 버전이 그보다 낮은 앱이 업데이트 대상이다. 같거나 높은 앱은 계속 사용할 수 있다.
- 값을 `NULL`로 비우면 강제 업데이트를 해제한다. 초기값도 `NULL`이다.
- 버전은 `숫자.숫자.숫자` 형식으로 입력한다. 잘못된 형식은 저장할 수 없어야 한다.
- 새 앱 배포는 운영자가 정한 값을 변경하지 않는다.
- 해당 사용자에게 새 앱을 설치할 수 있는 경로가 열린 것을 확인한 뒤 최소 지원 버전을 올린다. 현재 내부 배포에서는 대상 TestFlight 그룹의 설치 가능 여부를 확인한다.
- 구현 결과에는 Table Editor의 실제 테이블과 필드, 설정·해제 예시, 반영 시점을 적은 운영 안내가 있어야 한다.

## 앱에서 보이는 동작

- 앱은 로그인 전후 모두 최소 지원 버전을 조회한다. Supabase가 제공하는 Data API로 읽을 수 있으므로 값 전달만을 위한 별도 서버 API는 요구하지 않는다.
- 앱 시작과 다른 앱에서 돌아오는 시점에 확인한다. 복귀 시에는 마지막 확인 이후 일정 시간이 지난 경우만 조회한다.
- 낮은 버전은 업데이트 화면을 보여 주고 앱의 새 작업을 막는다. 지원하는 버전 또는 `NULL` 정책을 다시 받으면 이 화면을 해제한다.
- 업데이트 화면에서 설치 경로를 여는 행동과 정책을 다시 확인하는 행동을 제공한다. 다시 확인과 업데이트 화면으로 복귀하는 경우에는 일반 조회 간격을 무시한다.
- 설치 화면을 열었다는 이유로 업데이트 완료로 판단하지 않는다. 실제 설치된 앱 버전을 기준으로 판단한다. OTA 번들의 설정이나 빌드 번호를 최소 지원 버전과 비교하지 않는다.
- 설정은 일반 앱 사용자가 읽을 수만 있다. 로그인 여부와 무관하게 쓰기·삭제는 불가능해야 한다.

## 우선 적용할 가정

아래 값과 세부 동작은 운영자가 별도로 확정한 결정이 아니라 구현 가능한 기본안이다. 변경할 수 있다.

- 일반 복귀 시 확인 간격은 5분으로 둔다. 앱이 열린 채로 있으면 주기적으로 반복 조회하지 않는다.
- 정책 조회는 앱 시작을 무기한 막지 않는다. 5초 안에 확인하지 못하면 조회 실패로 처리한다.
- 조회 실패나 누락된 설정 때문에 새로 차단하지 않는다. 같은 실행에서 이미 차단을 확인했다면 재조회 실패만으로 풀지 않고 다시 확인할 수 있게 한다. 차단을 다음 앱 실행까지 영구 저장하지 않는다.
- 확인 도중 진행 중인 응답이나 저장이 있으면 그 작업을 손상시키지 않고 완료 또는 실패 처리가 끝난 뒤 업데이트 화면으로 전환한다.
- 플랫폼마다 같은 정책 형식을 사용하되 최소 지원 버전 값과 설치 경로는 구분한다. 현재 내부 배포의 설치 경로는 TestFlight다. 공개 스토어 경로는 실제 출시 때 설정하며 임의의 주소를 만들지 않는다.
- 업데이트 화면의 기본 문구는 `업데이트가 필요해요`, `플린을 계속 사용하려면 최신 버전으로 업데이트해 주세요`, 버튼은 `업데이트하기`, `다시 확인`이다. 화면 배치는 기존 앱 컴포넌트와 아래 화면 계약을 따른다. 별도 시각 시안은 아직 검토하지 않았다.

## 완료 조건

- 운영자가 Dashboard에서 값을 바꾸면 앱이나 API 서버를 다시 배포하지 않아도 다음 정책 조회에서 반영된다.
- 최소 지원 버전이 `1.2.0`일 때 `1.1.9`만 차단되고 `1.2.0`, `1.10.0`은 차단되지 않는다. 문자열 사전순으로 비교하지 않는다.
- `NULL`을 저장한 뒤 차단 화면에서 다시 확인하면 앱을 다시 설치하지 않고 차단이 풀린다.
- 로그인 전후에 정책을 읽을 수 있고 일반 사용자의 정책 변경 요청은 거절된다.
- 시작·복귀·수동 확인의 조회 시점과 중복 요청 제한이 관찰 가능하게 검증된다.
- 조회 실패, 설치 경로 열기 실패, 잘못된 응답에서 앱이 무한 대기하거나 업데이트 완료로 오판하지 않는다.
- 일반 OTA는 배너나 팝업 없이 다음 완전한 앱 실행에 적용된다.

## 한계와 남은 확인

- 이 기능이 없는 기존 앱에는 차단 화면을 표시할 수 없다. 먼저 조회 기능을 포함한 앱을 배포해야 한다.
- 같은 앱 버전의 특정 빌드만 차단할 수 없다. 이 한계는 단순한 정책을 위해 받아들인다.
- 앱 화면 차단은 서버 권한 검사나 보안상 구버전 요청 거절을 대신하지 않는다. 서버 전체의 버전별 접근 제한은 이번 범위가 아니다.
- 설정 조회 실패 시 사용을 허용하므로 항상 즉시 차단되는 정책이 아니다. 앱이 계속 열린 상태에서는 다음 확인 시점까지 변경이 반영되지 않는다.
- 공개 출시 전에 내부·공개 배포의 정책 조회 범위를 나눠야 한다. 현재 내부 배포와 공개 사용자에게 같은 설정을 무조건 적용하지 않는다.
- 공식 문서의 Table Editor, Data API와 grants/RLS 동작을 확인했다. 실제 테이블 생성, 권한 검사, 기기에서 업데이트 이동·재확인은 구현 때 검증한다.
