# 내부 테스트 자동 배포

## 확정 범위

2026-09-09 대화에서 합의한 PR 검증과 Supabase·Hono·iOS 내부 테스트 배포를 확정한다. 이번 문서는 구현 계약과 실제 원격 검증 기록을 함께 담는다.

## 사용자에게 보이는 결과

- 개발자는 PR에서 코드 검사, 타입 검사, 테스트 결과와 네이티브 구성 변경 라벨을 확인한다.
- 필요한 검사를 통과한 변경을 `main`에 합치면 관련 서비스만 올바른 순서로 배포된다.
- 내부 테스터는 기존 앱과 호환되는 변경을 EAS Update로 받는다. 새 앱이 필요하면 `Flyn Internal`에서 TestFlight 빌드를 설치한다.
- 개발자는 배포한 커밋, 서비스별 실행 결과와 실패한 단계를 확인할 수 있다. 실행 요청 성공을 배포 완료로 표시하지 않는다.
- 사용자의 기존 로그인, 플레이 기록과 대화 기록을 배포 때문에 잃지 않는다. 제품 경험과 데이터의 소유권은 루트 `PRODUCT.md`와 기존 결정 계약을 따른다.

## 합의한 흐름

```text
PR 생성·수정
  ├─ 코드 검사·타입 검사·테스트
  ├─ DB 관련 변경의 전용 검사
  └─ 네이티브 fingerprint 비교·라벨 표시
        ↓ 필요한 검사 통과 후 main에 합치기
GitHub Actions
  → Supabase 마이그레이션 적용·확인
  → 변경된 Edge Function 배포·확인
  → Hono의 Vercel 배포·확인
        ↓ 같은 커밋의 서버 준비 완료
EAS Workflows
  ├─ 호환되는 배포용 빌드 있음 → EAS Update
  └─ 호환되는 배포용 빌드 없음 → EAS Build → Submit → TestFlight
```

변경 없는 단계는 건너뛴다. 건너뛰기와 실패를 구분하며, 실패한 단계에 의존하는 배포는 시작하지 않는다. 앱이 직접 Supabase를 사용하는 경로에도 같은 순서와 이전 버전 호환성 규칙을 적용한다.

## PR 검증

### 공통 검사와 fingerprint 라벨

- 코드 검사·타입 검사·자동 테스트 실패를 합치기 전에 확인하고 차단한다. 기존 수동 호출형 Claude workflow와 코드 리뷰 소유권은 바꾸지 않는다.
- 모바일과 관련 공유 의존성이 바뀌면 PR의 네이티브 구성 차이를 표시한다. `Fingerprint:compatible`은 비교 대상과 차이가 없다는 뜻이고, `Fingerprint:changed`는 차이가 있다는 뜻이다.
- 라벨은 검토 정보다. 테스트 통과, 기기 검증 완료나 배포 가능한 빌드의 존재를 보장하지 않는다. 계산 실패를 compatible로 표시하지 않는다.
- 네이티브 변경은 새 빌드·기기 검증 필요 여부를 PR에서 검토한다. 배포할 때는 PR 라벨을 신뢰해 분기를 생략하지 않고 실제 호환 빌드를 다시 확인한다.

### DB 관련 PR의 기본 검사

- 스키마, 마이그레이션, seed, DB 테스트, 생성 타입과 DB 검증에 영향을 주는 설정·도구 변경을 감지한다. 관련 없는 화면·문서 변경 때문에 DB를 시작하지 않는다.
- 매 검사에 격리된 임시 로컬 Supabase DB를 사용한다. 운영 데이터와 운영 자격 증명을 사용하지 않으며, 검사가 끝나면 임시 자원을 정리한다. 상시 스테이징 DB나 원격 Supabase 브랜치를 만들지 않는다.
- 빈 DB에서 전체 마이그레이션과 테스트에 필요한 seed를 적용할 수 있어야 한다.
- DB lint가 발견한 오류, 기존 pgTAP 테스트 실패, 생성한 TypeScript 타입과 커밋한 타입의 차이를 실패로 표시한다.
- 선언형 스키마와 마이그레이션의 차이로 누락된 구조 변경을 찾는다. DML과 일부 권한 등 자동 diff의 사각지대는 테스트와 검토로 보완한다. 비교가 불완전하거나 실패했는데 일치로 표시하지 않는다.
- 기준 브랜치에 있던 마이그레이션의 수정·삭제를 감지해 차단한다. 아직 배포하지 않은 이력을 정리할 예외는 자동 통과시키지 않고 별도로 검토한다.
- 로컬 개발자의 검증 책임은 유지한다. CI는 그 검증을 PR에서 재현하는 추가 확인이다.

### 기존 데이터에 영향을 주는 변경의 추가 검사

- 데이터 변환, 열 타입 변경, 기존 행에 적용할 새 제약 조건 등에는 이전 스키마와 대표 데이터에 새 마이그레이션을 적용하는 보존 검사를 요구한다.
- 작성자는 해당 변경이 보존해야 할 행, ID, 외래키와 값의 의미를 명시하고 그 결과를 확인한다. 대표 데이터는 합성 데이터이며 운영 데이터를 가져오지 않는다.
- 모든 DB PR에서 범용 업그레이드 검사를 강제하지 않는다. 빈 테이블 추가와 기존 데이터 변환의 검증 부담을 구분한다.
- 컬럼 삭제 등 되돌리기 어렵거나 이전 앱을 깨뜨리는 변경은 별도 검토·승인 없이는 자동 배포하지 않는다. 승인만으로 이전 앱 호환성 요구가 사라지지 않는다.

## 배포 계약

- 전체 순서는 GitHub Actions가 관리하고 모바일 배포의 fingerprint·Update·Build·Submit은 EAS Workflows가 맡는다.
- 검사와 서비스별 배포는 동일한 커밋을 사용한다. 승인이나 실행이 늦어져도 당시의 최신 `main`으로 바꾸지 않는다.
- Supabase에는 커밋하고 검증한 미적용 마이그레이션만 적용한다. 적용 대상 확인은 실행 검증과 구분한다. 운영에서 마이그레이션을 생성하거나 DB를 초기화하지 않는다.
- 마이그레이션을 확인한 뒤 필요한 Edge Function과 Hono를 배포한다. Hono가 준비됐는지와 기본 요청·인증 경계가 유지되는지 확인한 뒤 앱을 배포한다.
- 같은 API를 Vercel의 별도 자동 배포와 GitHub Actions가 중복 배포하지 않는다. EAS도 `main`에 독립적으로 반응해 서버보다 먼저 배포하지 않는다.
- 운영 배포는 한 번에 하나씩 진행한다. 중단·재시도가 진행 중인 마이그레이션을 무작정 끊거나 이미 시작된 원격 배포를 중복 생성하지 않아야 한다. 실패 이후의 재시도는 완료된 단계와 원격 상태를 확인한다.
- Supabase 적용 후 Hono가 실패해도 DB를 자동으로 되돌리지 않는다. 이전 API·앱이 계속 작동하는 호환 변경을 먼저 배포하고, 실패 결과를 남긴다.
- 공통 패키지와 의존성 변경의 영향을 포함해 배포 대상을 고른다. 문서만 바뀌면 배포하지 않는다. 이전 배포 실패로 남은 변경을 단순한 최근 커밋 경로 비교로 놓치지 않는다.
- DB seed·콘텐츠와 Auth 설정을 매 배포마다 일괄 덮어쓰지 않는다. 해당 변경은 명시적으로 검토한 배포 대상으로 다룬다.

## 모바일 배포와 환경

- 첫 자동화 대상은 iOS의 `Flyn Internal`이다. 공개 App Store 출시와 Android 스토어 배포는 포함하지 않는다.
- EAS Update를 도입하고 runtimeVersion의 fingerprint 정책으로 네이티브 호환성을 구분한다. 대상 플랫폼·배포 프로필·채널과 호환성이 맞는 빌드를 기준으로 판단한다.
- 성공한 빌드가 존재한다는 사실과 테스터가 설치할 수 있다는 사실을 구분한다. 기존 빌드의 제출 실패나 Apple 처리 대기를 무시한 채 배포 완료로 표시하지 않는다.
- 내부 테스트용 업데이트 채널을 사용하고, 앱의 공개 환경 변수는 현재 운영 백엔드를 가리킨다. EAS 환경과 업데이트 채널은 서로 다른 개념이며, 채널을 나눈다고 DB가 격리되는 것은 아니다.
- 빌드·fingerprint·업데이트는 같은 대상의 환경 설정을 명시적으로 사용한다. 개발자의 로컬 환경 파일이나 설정 검증 우회값을 실제 배포에 사용하지 않는다.
- EAS Update를 지원하는 새 TestFlight 빌드를 먼저 설치해야 한다. 기존에 Update 없이 만든 앱에 OTA만 보내서 기능을 추가할 수 있다고 안내하지 않는다.
- EAS Update는 모든 기기에 즉시 적용되는 강제 업데이트가 아니다. 적용·재실행 동작을 실제 기기로 확인하고, 오래된 앱도 계속 API·DB를 사용할 수 있게 한다.

## 완료 조건

1. 잘못된 코드·타입·테스트를 포함한 PR이 실패하고 정상 PR은 통과한다.
2. 네이티브 변경 유무에 따라 PR 라벨이 갱신되며 서로 반대인 라벨이 동시에 남지 않는다. 계산 오류는 별도로 드러난다.
3. DB SQL 오류, 권한 테스트 실패, 생성 타입 누락, 감지 가능한 선언형 스키마 누락과 기존 마이그레이션 변경을 각각 실패 사례로 확인한다.
4. 데이터 변환 사례에서 이전 데이터에 새 마이그레이션을 적용해 ID·관계·값 보존을 확인한다. 일반 PR에 이 추가 검사를 무조건 요구하지 않는다.
5. DB와 무관한 변경에서는 임시 DB 검사가 건너뛰어지고, 필요한 공통 검사의 결과는 계속 남는다.
6. DB 또는 API 배포 실패 시 후속 모바일 배포가 시작되지 않는 것을 확인한다. 변경 없음은 실패로 처리하지 않는다.
7. 서비스별 커밋과 원격 실행 결과가 연결되며, 동시에 요청한 배포가 서로를 덮어쓰거나 중복 제출하지 않는다.
8. Update 호환 빌드가 있는 변경은 새 네이티브 빌드 없이 내부 채널에 배포된다. 호환 빌드가 없는 변경은 새 빌드와 제출 결과로 이어진다.
9. 실제 iPhone에서 최초 Update 지원 빌드 설치와 후속 OTA 수신을 확인한다. Metro 없이 셀룰러로 로그인·기존 기록 조회·AI 응답을 확인한다.
10. PR 검사에 운영 비밀값·데이터가 전달되지 않고, 배포 로그와 앱 번들에도 서버 비밀값이 노출되지 않는다.
11. 문서만 바꾼 변경은 원격 배포를 만들지 않는다. 실패한 배포 재시도는 누락된 변경을 포함하고 같은 원격 작업을 중복 생성하지 않는다.

## 가정과 보류

- 가정: 내부 업데이트 채널의 문자열 이름은 구현 때 정할 수 있는 운영 이름이다. 이름 자체가 별도 백엔드나 앱 ID 분리를 뜻하지 않는다.
- 가정: PR의 DB lint는 오류를 실패 기준으로 시작한다. 경고를 모두 차단할지는 실제 기준선에서 잡음을 확인하고 정한다.
- 보류: 공개 출시 채널·승인·단계적 배포, Android 제출, Supabase Branching, 장기 스테이징 환경과 원격 CI E2E는 별도 결정한다. 그전에는 내부 iOS 채널과 현재 운영 백엔드만 자동 배포한다.
- 보류: 위험한 DB 변경 승인 UI·권한과 서비스별 최소 권한 토큰의 실제 발급 가능 여부는 구현 시 원격 설정으로 확인한다. 승인 장치가 없으면 위험한 변경의 자동 배포를 열지 않는다.
- 보류: 이전 앱 지원을 종료할 기준과 강제 업데이트는 별도 결정한다. 그전에는 옛 API 요청·응답과 직접 DB 접근의 호환성을 유지한다.
- 보류: 실패 알림의 외부 수신 채널은 정하지 않았다. 이번 범위에서는 GitHub와 각 서비스의 실행 결과로 확인한다.

## 남은 위험과 확인 근거

- 임시 DB와 합성 데이터는 운영의 데이터 규모, 잠금 시간, 모든 행의 형태를 재현하지 않는다. 운영의 파괴적 변경은 별도 검토 대상이다.
- fingerprint는 네이티브 호환성 검사이지 기능 정상 동작의 증명이 아니다. PR 비교와 배포용 빌드 조회는 서로 대체하지 않는다.
- 현재 저장소는 Expo SDK 57, EAS CLI 24.0.0, Supabase CLI 2.113.0, Bun 1.4.0을 고정한다. GitHub Actions와 EAS Workflows의 실제 원격 실행으로 이 조합을 확인했다.
- Supabase CLI 도움말 조회가 로컬 telemetry 파일 쓰기 권한으로 실패한 적이 있다. 공식 문서만으로 CLI 실행 검증이 끝났다고 보지 않는다. 구현 때 격리된 검증 환경에서 명령·종료 코드와 schema diff 한계를 확인한다.
- [Supabase 공식 CI 예제](https://github.com/supabase/supabase-action-example/blob/main/.github/workflows/ci.yaml)는 임시 DB, lint, pgTAP, 생성 타입 비교를 보여준다. 해당 예제의 `latest`, 운영 비밀값을 사용하는 별도 dry-run 작업과 환경 구성을 그대로 복사하지 않는다.
- [선언형 스키마](https://supabase.com/docs/guides/local-development/declarative-database-schemas)의 diff 사각지대, [EAS 배포 예제](https://docs.expo.dev/eas/workflows/examples/deploy-to-production/), [runtimeVersion](https://docs.expo.dev/eas-update/runtime-versions/), [EAS 외부 실행 API](https://docs.expo.dev/eas/workflows/rest-api/)를 확인했다. 공식 문서는 복사하지 않고 구현 시 원본을 다시 읽는다.
- Dearly의 과거 `4546cdbb` 직전 모바일 배포 분기와 현재 PR 라벨·Supabase 단계 분리를 참고했다. 현재 운영 성공을 검증한 템플릿으로 취급하지 않는다.
- 기술 문맥: Expo/EAS와 Supabase 공식 스킬은 저장소에 이미 있고 Vercel 배포 스킬은 현재 도구 환경에 있다. Hono는 기존 공식 CLI 문서 경로를 유지한다. GitHub Actions 전용 공식 스킬은 이번 확인에서 확보하지 않았으므로 공식 문서를 직접 읽는다. 새 스킬은 설치하지 않았다. 장치·클라우드 실행 검증은 구현 완료 조건으로 남긴다.
