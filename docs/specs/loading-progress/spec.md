# 로딩 진행 표시

상태: 승인. 사용자가 2026-09-10에 화면 전체 로딩의 상태 문구, 로딩 문구의 마침표, 화면에 나오지 않는 진행 저장 표시를 함께 정했다.

## 결과와 범위

### 화면 전체 로딩

- 화면 전체를 대기에 쓰는 두 자리에서 상태 문구를 없앤다. 앱을 열고 로그인과 프로필을 확인하는 동안, 그리고 에피소드에 들어가 대화를 읽는 동안이다. 화면 중앙에는 진행 표시 하나만 남는다.
- 이 두 자리의 진행 표시는 36px로 그린다. 문구 옆에 서는 표시의 크기를 쓰지 않는다.
- 1초 기준을 유지한다. 1초 안에 끝나면 진행 표시를 띄우지 않고, 1초를 넘겨야 나타난다. 로그인 확인과 프로필 확인은 지금처럼 하나의 대기로 세고, 단계가 바뀌어도 시간을 다시 세지 않는다.
- 화면 읽기는 두 자리에서 무엇을 기다리는지 계속 말한다. 화면에 보이지 않는 이름으로 전달한다.
- 진행 표시의 색 규칙은 그대로다. iOS는 `muted`, Android는 `accent`다.

### 화면 일부 로딩

- 화면의 일부만 기다리는 자리는 상태 문구를 유지한다. 인증 코드 확인과 표현 교정 확인이 그렇다. 문구의 내용, 자리와 크기를 바꾸지 않는다.
- 로딩 문구의 마침표를 화면 문구 규칙에 맞춘다. 지금 빠져 있는 인증 코드 확인 문구에 마침표를 붙인다. 화면에서 사라지고 화면 읽기 이름으로 남는 대화 읽기 문구에도 붙인다.
- 에피소드 마무리의 저장 중 표시를 없앤다. 문구와 표시, 그것을 켜는 상태를 함께 지운다.

## 완료 기준

- 앱을 열고 1초가 지나도 화면에 글자가 없다. 화면 중앙에서 진행 표시 하나만 돈다. 로그인 확인에서 프로필 확인으로 넘어가도 화면이 바뀌지 않는다.
- 에피소드에 들어가 1초가 지나도 같다. 네이티브 헤더와 뒤로 가기는 그대로 있고, 그 아래 남은 본문의 중앙에 진행 표시가 선다.
- 두 자리 모두 1초 안에 끝나면 진행 표시가 한 번도 보이지 않는다.
- iOS와 Android, 밝은 화면과 어두운 화면에서 진행 표시가 배경에 묻히지 않는다. 각 운영체제의 진행 표시 모양을 유지한다.
- 화면 읽기를 켜고 두 자리에 들어가면 무엇을 기다리는지 읽는다. 진행 중이라는 상태도 함께 전달한다.
- 확인이 끝나면 실제 상태에 맞는 화면이 열리고, 실패하면 기존 오류 화면과 다시 시도 경로가 그대로 열린다.
- 화면에 보이는 로딩 문구와 화면 읽기로만 전하는 로딩 이름이 모두 마침표로 끝난다.
- 인증 코드 확인과 표현 교정 확인의 문구가 지금과 같은 자리에 같은 크기로 보인다.
- 에피소드가 끝나도 저장 중이라는 표시가 나타나지 않는다. 마무리 카드의 결말, 다음 이야기 예고와 두 버튼은 그대로다. 다음 화 시작 버튼의 진행 상태도 지금처럼 동작한다.
- 이미 사용 중인 화면의 백그라운드 갱신은 여전히 화면 전체 로딩으로 바뀌지 않는다.

## 결정 이유와 가정

- 화면 전체가 대기의 대상일 때 문구는 읽을 대상이 아니라 화면을 채우려고 놓인 글이다. 무엇을 기다리는지는 사용자가 방금 한 행동이 이미 말해 준다. 앱을 열었으니 앱이 열리는 중이고, 에피소드를 눌렀으니 그 대화를 여는 중이다.
- 반대로 화면의 일부만 기다릴 때는 화면의 나머지가 살아 있다. 그래서 무엇이 기다리는 중인지 그 자리가 스스로 말해야 한다. 이것이 두 경우를 가르는 기준이다.
- 36px은 세 크기를 화면 한가운데에 나란히 놓고 눈으로 비교해 골랐다. iOS `ActivityIndicator`의 `large`가 36pt, Material `CircularProgressIndicator`의 기본이 40dp라 두 운영체제가 화면 중앙 로딩에 쓰는 범위 안에 있다. 지금의 20px은 문구 줄높이에 맞춰 정한 값이라 옆에 설 글자가 없어지면 근거도 사라진다.
- 진행 표시까지 없애지 않는 이유는 멈춘 빈 화면과 구분하기 위해서다. 이것은 문구를 넣었던 기존 결정의 근거이기도 했고, 문구를 빼도 그대로 남는다.
- 마침표 규칙은 한쪽으로 명확하다. 로딩 문구는 모두 평서문이라 붙이는 쪽인데, 같은 종류의 문구 여덟 중 셋만 빠져 있었다. 의도가 아니라 빠뜨린 것으로 본다.
- 에피소드의 저장 중 표시를 지우는 이유는 화면에 나올 수 없기 때문이다. 저장 주체가 서버 하나로 정리되면서 앱이 기다릴 저장이 사라졌고, 그 표시를 켜는 값은 도입된 뒤로 줄곧 꺼져 있었다. 화면에 나올 수 없는 표시를 남기면 다음 사람이 그것이 동작한다고 믿는다.
- 가정: 화면 읽기 이름은 기존 접근성 알림 문구를 그대로 쓴다. 앱 진입은 `로그인 상태 확인 중`과 `프로필 확인 중`, 에피소드는 대화를 불러오는 중임을 알리는 짧은 문구다. 화면에 보이지 않는 이름으로 상태를 전하는 방식은 채팅의 답변 대기와 아이디 확인이 이미 쓴다. 뒤집을 수 있는 기본값이다.
- 가정: 화면 전체 로딩 두 자리의 진행 표시는 같은 크기를 쓴다. 하나는 헤더가 없고 하나는 있지만, 둘 다 남은 본문 전체가 대기의 대상이라는 점이 같다. 뒤집을 수 있는 기본값이다.

## 제외와 한계

- 버튼과 컨트롤 안의 진행 표시, 목록 화면의 빈 상태, 이미지 로딩은 바꾸지 않는다.
- 화면 일부 로딩의 문구 내용과 자리, 크기는 바꾸지 않는다. 마침표만 맞춘다.
- 1초 기준의 값을 다시 정하지 않는다. 실제 작업 시간 측정이나 사용자 검증에서 이 기준이 맞지 않는다는 결과가 나오면 그때 다시 본다.
- 저장을 기다리는 상태를 앱에 다시 만들지 않는다. 저장 주체를 서버 하나로 두는 지금 설계를 이 작업이 다시 열지 않는다.
- 스켈레톤은 고르지 않았다. 화면 전체 로딩 두 자리 모두 들어올 내용의 뼈대를 미리 그릴 만한 구조가 없다.
- 위험: 화면 읽기 이름이 화면에 보이지 않으므로, 나중에 이 문구가 낡아도 화면을 보는 것만으로는 알 수 없다. 채팅의 답변 대기가 이미 같은 상태다.
- 위험: 로컬 스택에서는 인증 코드 확인, 대화 읽기, 표현 확인이 모두 1초 안에 끝나서 진행 표시가 나타나는 것을 화면으로 확인하기 어렵다. 기존 결정 계약이 같은 한계를 이미 기록했다.
