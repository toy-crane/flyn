# 배포 승인을 PR로 옮긴다

상태: 승인. 2026-09-11 사용자가 merge를 배포 승인으로 삼고, 파괴적 마이그레이션 감지를 기계에 맡기고, Codex 리뷰를 필수로 하고, 운영 환경 이름을 `production`으로 정했다.

## 배경

지금은 `main`에 합친 뒤 DB 배포와 Edge 배포가 각각 `flyn-production-review` 환경 승인을 기다린다. 승인 화면에는 SQL도 diff도 보이지 않고, 앞선 실행이 실패해 기준 커밋이 없으면 마이그레이션이 없는 커밋도 두 번 승인해야 한다. 실행 #81이 그랬다. 마이그레이션의 데이터 영향은 작성자(대개 에이전트)가 `impact.json`에 스스로 분류하고 CI는 그 값을 믿는다. 실제로 있었던 테이블 삭제는 `preserve`로 분류됐고 CI는 막지 않았다. 배포가 막힌 뒤에는 CLI로 손수 운영 API를 올렸다.

조사한 기준선(Supabase 공식 환경 가이드와 Branching, squawk, Atlas, strong_migrations)은 모두 같다. PR이 게이트이고 merge하면 자동 배포한다. 위험은 린터가 SQL에서 잡고, 작성자는 의도했다는 표시와 이유만 남기고, 사람이 PR에서 읽고 합친다. 근거는 [검증과 내부 테스트 배포](../../decisions/continuous-delivery.md)의 보존할 근거에 둔다.

## 사용자에게 보이는 결과

- `main`에 합친 커밋은 사람에게 다시 묻지 않고 DB, Edge Function, API, 모바일 순서로 끝까지 배포된다. GitHub Deployments에는 `production` 환경 하나만 남는다.
- 새 마이그레이션에 테이블이나 열을 지우는 문장이 있으면 PR 대화에 어느 파일 몇째 줄이 걸렸는지 댓글이 달리고 검사가 실패한다. 사람은 그 줄을 열어 바로 위 주석의 이유를 읽고, 맞으면 승인 라벨을 붙인다. 라벨이 붙으면 검사가 통과한다.
- 승인 뒤에 새 커밋이 push되면 라벨이 떨어지고 검사가 다시 실패한다. 사람이 읽은 SQL과 합쳐지는 SQL은 항상 같다.
- Codex 리뷰가 달리지 않은 PR은 합칠 수 없다. 리뷰가 달리면 사람이 손대지 않아도 검사가 통과로 바뀐다.
- `impact.json`이 없어진다. 마이그레이션 작성자는 지우는 문장 위에 이유를 주석으로 쓰고, 데이터 변환에는 지금과 같은 보존 테스트 폴더를 둔다.
- PR 검사의 테스트 잡이 Linux에서 돈다. 개발 도구의 macOS 전용 테스트는 CI에서 돌지 않고 개발자의 Mac에서만 돈다.

## 확정한 동작

### merge가 배포 승인이다

- `main`에 커밋이 들어오면 배포 잡은 어떤 환경 승인도 기다리지 않는다. `flyn-production-review` 환경과 승인 환경을 고르는 판정 단계를 없앤다.
- 운영 배포 잡은 `production` 환경 하나를 쓴다. 이 환경은 보호된 브랜치에서만 배포하도록 남기고 필수 승인자를 두지 않는다. `flyn-production-automatic`은 지운다.
- `main`은 PR을 거치지 않은 push를 받지 않는다. 브랜치 보호에 PR 필수를 켠다.
- 배포 잡 이름에서 승인을 뜻하는 표현을 뺀다. 필수 검사 이름 `Required validation`과 `Required database validation`은 그대로 둔다.
- 운영 배포의 유일한 복구 경로는 실패한 실행을 다시 실행하거나 새 커밋을 합치는 것이다. 사람이나 에이전트가 CLI로 운영 API, Edge Function, DB, 모바일을 직접 올리지 않는다. 손으로 올린 배포는 요청 ID가 없어 파이프라인이 이어받지 못한다.

### 파괴적 마이그레이션은 PR에서 감지하고 승인한다

- PR에 새로 추가된 마이그레이션 파일만 squawk로 검사한다. 기준 브랜치에 이미 있던 마이그레이션은 보지 않는다.
- squawk가 걸린 문장을 PR 댓글로 올린다. 댓글에는 파일, 줄, 규칙과 규칙 설명이 들어간다. 걸린 것이 없으면 그 사실을 짧게 남기거나 댓글을 남기지 않는다.
- 테이블 삭제, 열 삭제, TRUNCATE CASCADE처럼 데이터가 사라지는 규칙에 걸린 문장은 다음 둘을 모두 갖춰야 검사가 통과한다. 문장 바로 위에 이유 주석이 있고, PR에 `DB:destructive-approved` 라벨이 있다.
- 데이터가 사라지는 규칙에는 squawk의 무시 주석을 쓸 수 없다. 무시 주석이나 파일 전체 무시가 있으면 검사가 실패한다. 걸린 문장은 항상 댓글에 나타나야 한다.
- 이유 주석은 마이그레이션을 쓰는 쪽이 쓴다. 이 저장소에서는 대개 에이전트다. 무엇이 사라지는지, 왜 지워도 되는지, 사용자가 언제 무엇을 결정했는지를 적는다.
- 승인 라벨은 사람만 붙인다. 에이전트는 어떤 경우에도 이 라벨을 붙이지 않는다.
- PR에 새 커밋이 push되면 검사가 자기 실행에서 먼저 승인 라벨을 떼고 나서 판정한다. 새 커밋 뒤에는 이전 승인이 어떤 순간에도 통과 조건이 되지 않는다. PR 제목이나 본문만 고친 경우에는 라벨을 떼지 않는다.
- 이 검사는 `ci.yml`이 아니라 라벨 이벤트와 Codex 댓글 이벤트에 반응하는 별도의 작은 PR 워크플로가 맡는다. `ci.yml`이 라벨 이벤트로 다시 도는 일은 없다. 이 검사는 브랜치 보호의 필수 검사로 등록한다.

### Codex 리뷰는 필수다

- PR의 head 커밋에 Codex 리뷰가 달려 있어야 검사가 통과한다. Codex는 지적이 있든 없든 리뷰를 마치면 요약 댓글에 리뷰한 커밋과 완료를 적는다. 그 댓글이 바뀌면 검사가 다시 돌고, head 커밋의 리뷰가 끝났다고 적혀 있을 때만 통과한다. PR을 열 때 Codex가 바로 남기는 진행 안내는 리뷰로 치지 않는다.
- 커밋을 더 push하면 head가 바뀌므로 Codex를 다시 부른다. `merge` 작업을 맡은 에이전트는 리뷰가 달릴 때까지 기다리고, 리뷰가 짚은 내용을 사용자에게 보여 준 뒤 합친다.

### impact.json을 없앤다

- 새 마이그레이션에 `impact.json`을 요구하지 않는다. 기존 파일 열두 개는 지운다. 이유는 마이그레이션 PR과 운영 기록에 이미 남아 있다.
- 보존 테스트는 폴더가 있으면 실행한다. 새 마이그레이션과 같은 버전의 폴더에 이전 스키마용 합성 데이터와 pgTAP 검사가 있으면 CI가 지금처럼 돌리고, 기존 폴더의 파일이 바뀌어도 돌린다.
- 보존 테스트를 언제 붙일지는 CI가 강제하지 않는다. 데이터 변환에 보존 테스트를 요구하는 일은 Codex 리뷰와 `supabase-reviewer` 검토 계약이 맡는다.

### 필요 없어진 것을 지운다

- 운영 연결만 읽어 보던 수동 워크플로를 지운다. 배포 잡의 성공이 같은 사실을 증명한다.
- 승인 환경 판정, `impact.json` 검사와 그 테스트를 지운다.

### 개발 도구 테스트는 CI 밖에 둔다

- 시뮬레이터 반납처럼 macOS 명령에 기대는 개발 도구 테스트는 macOS가 아닌 곳에서 건너뛴다. CI의 테스트 잡은 Linux에서 돌고, 개발자의 Mac에서는 지금처럼 돈다.
- 이 항목은 다른 항목과 독립적으로 전달할 수 있다.

## 완료 조건

1. 새 마이그레이션이 없는 PR을 합치면 `main` 실행이 승인 대기 없이 대상 서비스를 모두 배포한다. Deployments에 `production`만 남고 `flyn-production-review`와 `flyn-production-automatic`은 없다.
2. 앞선 `main` 실행이 실패한 뒤 다음 커밋을 합쳐도 승인 대기가 생기지 않고, 마지막 성공 이후의 변경이 모두 배포된다.
3. 테이블을 지우는 새 마이그레이션 PR은 PR 댓글에 파일과 줄이 나타나고 필수 검사가 실패한다. 이유 주석과 승인 라벨을 갖추면 통과한다. 그 뒤 커밋을 push하면 라벨이 떨어지고 다시 실패한다.
4. 데이터가 사라지는 규칙에 squawk 무시 주석을 쓴 PR은 검사가 실패한다.
5. 기준 브랜치에 이미 있는 테이블 삭제 마이그레이션 때문에 다른 PR이 실패하지 않는다.
6. Codex 리뷰가 없는 PR은 필수 검사가 실패하고, 리뷰가 달리면 사람이 손대지 않아도 통과한다.
7. `impact.json` 없이 마이그레이션 PR이 통과한다. 보존 테스트 폴더가 있는 마이그레이션은 그 테스트가 실행되고, 폴더가 없으면 실행되지 않는다.
8. `main`에 직접 push하면 GitHub이 거부한다.
9. 운영 연결 읽기 워크플로와 승인 환경 판정 코드가 저장소에 없다.
10. PR 검사의 테스트 잡이 Linux 러너에서 통과하고, 같은 테스트 명령이 macOS에서는 개발 도구 테스트까지 실행한다.
11. 결정 계약과 에이전트 지침이 새 규칙을 담는다. 에이전트는 승인 라벨을 붙이지 않고, Codex 리뷰를 기다려 보여 주고, CLI로 운영 배포를 하지 않는다.

## 가정

- 승인 라벨 이름은 `DB:destructive-approved`다. 라벨을 떼는 일은 검사 자신이 한다. 떼는 것은 신뢰를 줄이는 방향이라 PR의 코드가 해도 fingerprint 계약의 "main 코드만 라벨을 쓴다" 원칙과 충돌하지 않는다. fork PR은 라벨을 뗄 권한이 없어 검사가 실패로 남는다.
- 이유 주석은 걸린 문장 바로 윗줄에 `-- 삭제 이유:`로 시작하는 한 줄 이상으로 쓴다. 검사는 이 접두사로 이유 주석을 알아본다.
- squawk는 고정 버전으로 설치한다. 데이터가 사라지는 규칙만 라벨 승인 대상이고, NOT NULL 해제와 잠금·인덱스 관련 규칙은 댓글로 보이되 merge를 막지 않는다. Supabase가 마이그레이션을 트랜잭션 안에서 실행한다고 보고 그에 맞는 설정을 쓰되, 구현 때 설치한 버전의 문서로 확인한다.
- 2026-09-11 확인: squawk는 파일을 해석하지 못하면 문법 오류만 내고 그 파일의 다른 규칙을 건너뛴다. 그러면 뒤에 있는 삭제 문장을 볼 수 없으므로, 문법 오류가 있는 파일은 사람이 전체를 읽고 라벨을 붙여야 통과한다. 무시 주석은 줄 주석뿐 아니라 블록 주석과 줄 끝 주석에 쓴 것도 찾는다. squawk가 그 형태도 따르기 때문이다.
- Codex 리뷰 필수는 head 커밋 기준이다. 커밋마다 Codex를 다시 부르는 일이 부담스러우면 "PR에 리뷰가 하나라도 있으면 통과"로 바꿀 수 있다.
- PR은 모두 저장소 소유자가 연다. fork PR의 댓글 쓰기 권한과 라벨 정리는 다루지 않으며 기존 fingerprint 계약의 fork 취급을 따른다.
- 개발 도구 테스트는 실행 환경이 macOS가 아니면 건너뛰는 방식으로 CI에서 뺀다. 테스트 목록에서 제외하는 방식도 가능하다.

## 범위 밖

- 파괴적 변경을 어떻게 안전하게 쓰는지(expand·contract, 늦춘 삭제)는 다루지 않는다. 이 작업은 감지와 승인 자리를 옮긴다.
- 스테이징 환경, Supabase Branching, Android 배포, 공개 출시는 그대로 별도 결정이다.
- Vercel과 EAS의 배포 조회 방식, 기준 커밋 판정은 바꾸지 않는다. 관련 다듬을 점은 [CI 변경 판정과 배포 조회에 남은 다듬을 점](../../follow-ups/ci-change-judgment-and-delivery-polish.md)이 든다.

## 남은 위험

- squawk의 데이터 손실 규칙은 테이블 삭제, 열 삭제, TRUNCATE CASCADE다. 일반 TRUNCATE, DELETE, 함수 안에 숨은 삭제는 잡지 못한다. 그 부분은 Codex 리뷰와 `supabase-reviewer`가 맡는다. 감지가 안 걸린 것을 안전의 증거로 쓰지 않는다.
- Codex 연동이 멈추면 모든 PR이 막힌다. 사용자가 필수로 받아들였다.
- 승인 라벨과 merge 클릭은 둘 다 사용자 계정으로 에이전트가 할 수 있다. 막는 것은 지침이지 권한이 아니다.
- 선언형 diff가 만드는 테이블 drop 후 재생성은 파괴적 규칙에 걸려 승인이 필요하다. 그 경우도 사람이 봐야 하는 변경이므로 의도한 동작으로 본다.
